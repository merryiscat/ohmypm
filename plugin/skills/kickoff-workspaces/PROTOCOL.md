# ohmyPM 2.0 작업 프로토콜

프로젝트와 작업 환경을 분리한다. 실행기·절차·템플릿은 외부 불변 패키지, 역할별 모델·원문·승인·질문·증거는
Git 공통 디렉터리 `.git/ohmypm/`에 보존한다. 프로젝트 고유 규칙·빌드 설정·제품 설계는 프로젝트 자산이다 [P-16].

규칙마다 [P-nn]·규칙·이유·대신·출처를 한 자리에 둔다. 번호는 바뀌지 않고 다시 쓰지 않는다. 규칙은 결론이다 —
적용 전에 이유와 대신을 읽는다. 결론만 옮겨진 문장은 제약으로 굳는다(2026-09-23 실측) [P-20].
파생 문서(entry.md·SKILL.md·runtime.md·템플릿)는 규칙을 다시 쓰지 않고 [P-nn]을 인용한다. tests/test_docs.py가 지킨다.

## 접수와 설계

- [P-01] **수정 전 분류** — main은 읽기 조사 뒤, 수정하기 전에 `처리 경로(direct/pl) / 근거 / 요청 범위`를 사용자에게 알리고 route에 기록한다.
  이유: odin-3.0에서 분류 없이 구현이 시작돼 새 화면 요청이 pl 설계를 건너뛰었다. 파일 열람 로그만으로는 착수 여부를 입증할 수 없어 진입점이 기록을 요구한다.
  대신: 분류에 필요한 읽기 조사는 자유다. 정보가 모자라면 조사하거나 pl에서 사용자와 논의한다.
  출처: T-006 §5 v2 (2026-09-22, 사용자 "위 내용 추가해야해")

- [P-02] **pl 경로 판정** — 새 화면·사용자 기능/흐름·데이터/권한 계약·외부 연동·비가역 변경은 pl로 보낸다. 명확하고 작고 가역적인 수정만 direct다. 조사 중 범위가 커지면 수정 전에 재분류한다. 파일 수·예상 시간은 판정 기준으로 쓰지 않는다.
  이유: 이 부류는 되돌리기 비용이 크거나 사용자와 합의할 관찰 기준이 있어야 한다. 크기(파일 수·시간)는 위험과 다른 축이라 기준이 못 된다(임계치 상한은 2026-09-23 폐기).
  대신: 판단이 서지 않으면 pl로 보낸다 — pl에서 direct로 내리는 비용이 그 반대보다 싸다.
  출처: T-006 §5 v2 (2026-09-22); 2026-09-23 사용자 결정

- [P-03] **설계는 pl이 결정** — pl은 합의한 최고 성능 모델로 설계·완료 기준·검증 방법·소유 경로·하네스를 사용자와 정한다. 논의 왕복과 기준 개수에 상한을 두지 않는다.
  이유: 설계가 틀리면 그 뒤가 전부 헛돈다. 왕복·기준 상한은 설계를 임의로 잘라 놓침을 만들었다(왕복 상한은 0.8.0에서, 기준 8개 상한은 2026-09-23에 폐기).
  대신: 기준마다 관찰 가능한 입력·동작·통과 조건·검증 방법을 하나씩 붙여 개수를 스스로 제한한다.
  출처: 플러그인 0.8.0 (2026-09-19); 1.0.0 (2026-09-21); 2026-09-23 사용자 결정

- [P-04] **승인은 사용자, 판정은 pl** — main은 사용자 결정 파일 없이 approve하지 않고 pl verdict 없이 merge하지 않는다. main은 둘을 기록·전달한다.
  이유: 판정(action)과 확정 권한(authority)을 한 에이전트가 동시에 공급하면 독립 검문이 사라진다 — confused-deputy, 2026-08-23에 "명백히 keep"이라며 자동 커밋해 되돌린 실사고.
  대신: pl이 없으면 role-connect로 준비하고, 사용자에게 pl과 직접 대화할 위치를 안내한다.
  출처: mistakes 2026-08-23 confused-deputy; T-006 §5 v2 (2026-09-22)

- [P-05] **계약 고정** — main은 runtime pin·config·route·spec·manifest를 한 승인 digest로 묶어 고정하고, 실제 사용자 결정 파일이 있을 때만 approve한다.
  이유: 승인 뒤 어느 하나가 바뀌면 검증이 요청 원문과 어긋나고 판정이 뜻을 잃는다. 스냅샷 변조는 승인을 무효화한다.
  대신: 바뀌면 revise로 새 revision을 만들고 다시 승인받는다.
  출처: T-006 §4.3–4.4 (2026-09-22)

## 실행과 검증

- [P-06] **독립성이 입증된 work만 병렬** — 병렬은 소유 경로·의존성·포트·데이터가 겹치지 않음을 스펙에 적은 work끼리만 한다. 개수 상한은 없다.
  이유: 강제 병렬은 토큰 5배·지연 46~108%를 만들었다(0.7.0 실측). 상한 "2개"는 근거 없는 숫자라 2026-09-23 폐기.
  대신: 독립성 근거가 없으면 순차로 돌린다.
  출처: 플러그인 0.7.0 (2026-09-18); 2026-09-23 사용자 결정

- [P-07] **기준은 revision에 고정** — 완료 기준은 승인된 revision의 것이다. 바꾸려면 revise → 사용자 재승인 → 새 revision이며, 그 전까지 work·pl은 기준을 그대로 검증한다. 자동 검증 통과만으로 수동 기준을 pass로 적지 않는다.
  이유(inferred): 구현 도중 기준이 움직이면 검증이 요청 원문과 어긋나고 승인 digest가 뜻을 잃는다.
  대신: 기준이 틀렸으면 판정을 fail로 남기고 revise를 제안한다.
  출처: T-006 §4.4 (2026-09-22); 플러그인 0.6.0 요청 대조 (2026-09-18)

- [P-08] **판정은 증거에 묶인다** — pl 판정은 결과 commit·통합 base·spec revision·승인 digest에 묶이며, 코드 검토와 실제 동작 확인을 모두 거친다. 미실행은 통과가 아니다.
  이유: 어느 커밋을 어떤 기준으로 봤는지 없는 판정은 재현도 재검증도 안 된다.
  대신: 자동 검사만 통과했으면 fail 또는 미실행으로 남기고 실제 확인을 work에 돌린다.
  출처: T-006 §4·§8 C7·§5 v3 (2026-09-22)

- [P-09] **통합은 로컬 ff까지** — main은 깨끗한 등록 체크아웃에 pl 판정을 받은 결과만 fast-forward로 로컬 머지한다. 푸시·배포·추적 파일 정리 커밋·타 프로젝트 전환은 각각 사용자의 별도 요청으로만 실행한다.
  이유: 원격·이력은 되돌리기 어려운 경계라 사용자 확정 지점이다. 2026-08-23에 "명백히 keep"이라며 자동 커밋해 되돌린 사고가 있다.
  대신: 머지까지 끝내고 "푸시할까요"를 한 줄로 묻는다. 정리 커밋은 migration-apply 결과를 사용자가 검토해 직접 커밋한다.
  출처: mistakes 2026-08-23 confused-deputy; T-006 §1·§7.8 (2026-09-22)

- [P-10] **대역과 실증 구분** — 테스트 대역(fake)으로 통과한 항목을 실제 모델·Orca 검증 통과로 표시하지 않는다.
  이유: 1.0 검증에서 대역만 통과한 항목이 실증으로 읽혀, 실제 환경(Windows .CMD 셈)에서 main이 아예 못 뜨는 결함이 2.0.2까지 남았다.
  대신: 판정 표에 "통과(대역)"와 "통과(실제)"를 나눠 적는다.
  출처: T-006 §8 (2026-09-22); 2026-09-23 odin_3.0 실측

## 세션과 복구

- [P-11] **명시 연결만** — main/pl 세션은 role-connect와 context digest 수락으로만 연결된다. 플러그인 설치·doctor 통과는 전달 증거가 아니다.
  이유: 열려 있던 세션은 새 규칙을 읽지 않는다. 0.4.0~0.7.1 사이 23개 프로젝트가 옛 규칙서를 읽고 있었다.
  대신: 갱신 뒤엔 role-connect로 다시 연결하고 role-show로 accepted를 확인한다.
  출처: T-006 §5 (2026-09-22); 2026-09-19 재배포 기록

- [P-12] **불명은 죽음이 아니다** — pl 세션은 positive 종료(실행기가 남긴 종료 코드)나 최초 미등록일 때만 새로 만든다. 응답 지연·통신 실패·셸 idle은 불명 상태이며, 불명 상태에서 생성하거나 종료하지 않는다.
  이유: tui-idle·시간 경과로 죽었다고 보고 중복 생성하면 두 pl이 같은 상태를 건드린다. 생명주기 파일의 생성 식별자·종료 코드만이 증거다.
  대신: 불명이면 기다리거나 사용자에게 알린다. 확인은 role-show와 생명주기 파일로 한다.
  출처: T-006 §5 v3·§10 C6 (2026-09-22)

- [P-13] **outbox가 기억이다** — 질문·요청은 outbox에 보존하고 전송·수락·완료를 구분한다. 과거 generation/revision의 답은 보존하되 적용하지 않는다. 대화 이력에 연속성을 맡기지 않는다.
  이유: 세션은 끊기고 화면 파싱은 깨진다(0.9.0 실측). Git 공통 디렉터리의 이벤트만이 세션을 넘어 살아남는다.
  대신: 복구된 세션은 기존 기록(tasks·requests·outbox)을 읽고 해당 generation을 수락한 뒤 일한다.
  출처: T-006 §5 v3 (2026-09-22)

- [P-14] **종료는 취소가 아니다** — 세션이 끝나도 기록된 승인과 유효한 판정은 살아 있다. work는 승인 범위를 계속 수행할 수 있으나 필요한 pl 판정 전에는 머지하지 않는다.
  이유: 종료마다 승인을 다시 받으면 사용자가 같은 결정을 반복하고, 판정 없이 머지하면 P-04가 무너진다.
  대신: 새 pl에게 이어받은 revision과 위치를 안내하고 판정을 받는다.
  출처: T-006 §5 v3 (2026-09-22)

- [P-15] **전 역할 bypass** — 역할 세션은 기본 approval=bypass로 시작한다(Codex `--dangerously-bypass-approvals-and-sandbox`, Claude `--dangerously-skip-permissions`). 프로필에 `approval=default`를 적으면 CLI 기본 정책이다.
  이유: 승인 프롬프트는 안전장치가 아니라 사람이 온종일 읽고 누르는 일이 된다.
  대신: 안전은 런타임 가드(`scripts/guard.py`, deny 목록 대조만·모델 판단 없음)와 `disallowed_tools`가 맡는다. 무엇을 막을지는 등록 때 묻고 harness에 적는다.
  출처: 2026-09-22 사용자 "매번 데이터 승인해줄수 없음"(Codex pl, T-006 §추가 실행 설정) → 2026-09-23 사용자 결정으로 전 역할 확대(2.1.0)

- [P-16] **프로젝트 트리 무설치** — ohmyPM 운영 하네스(등록·갱신·해제·역할 세션 기동)는 프로젝트의 추적 파일·index·HEAD·AGENTS.md/CLAUDE.md·.gitignore·orca.yaml·.worktreeinclude를 수정하지 않고, `.claude/settings*`·`.githooks`·`core.hooksPath`는 읽지도 쓰지도 않는다.
  이유: 프로젝트 gitignore가 배포 파일을 삼켰고(2026-09-18·09-22, 4개 저장소), 버전마다 23개 프로젝트를 고쳐 커밋해야 했으며, 프로젝트 pre-commit 훅이 역할 정책과 얽혀 pl 커밋을 막았다(2026-09-19).
  대신: 훅 본체는 런타임 `scripts/guard.py`, 켤 목록은 `.git/ohmypm/project.json` harness → 기동 때 `--settings`로 얹는다. 지침은 세션 context로 전달한다. 훅을 안 쓴다는 뜻이 아니다.
  예외: 없음. 범위 밖 — 프로젝트 자산(llmwiki 위키·SessionStart 훅, plan.md)은 킥오프에서 사용자 요청으로 만들고 프로젝트가 소유한다.
  출처: T-006 §1·§3·§6 (2026-09-22)

## 업데이트와 전환

- [P-17] **업데이트는 미래 작업에만** — 진행 중 작업은 고정된 패키지 해시를 계속 쓴다. 패키지 누락·변조·schema 불일치는 실행을 거부하고, 참조 중인 패키지는 자동 제거하지 않는다.
  이유: 작업 도중 실행기가 바뀌면 판정의 재현 근거가 사라진다. 런타임은 내용 해시로 불변이라 "어느 빌드가 돌았나"가 증거가 된다.
  대신: 다음 작업부터 새 패키지를 쓴다. 바꾸려면 select-runtime으로 pin을 바꾼다.
  출처: T-006 §4.5–4.7 (2026-09-22)

- [P-18] **1.0 전환은 검토된 계획으로만** — 1.0 설치본은 자동 전환하지 않는다. migration-plan을 검토하고 그 digest로 apply하며, 사용자 수정·불명 소유·출처 불명 훅은 conflict로 보존한다. 활성 1.0 작업이 있으면 적용하지 않는다.
  이유: 이름만으로 소유권을 판정하면 사용자 파일을 지운다. 전환은 추적 파일을 지우는 명시적 프로젝트 변경이라 일반 갱신과 섞이면 안 된다.
  대신: 기존 1.0 작업은 보존된 1.0 실행기로 마무리한다. 정리 커밋은 사용자가 검토해 직접 한다.
  출처: T-006 §7 (2026-09-22)

- [P-19] **disable은 보존** — disable은 새 작업만 막고 증거·활성 작업·외부 패키지를 보존한다. 상태와 패키지 백업은 별도 요청이다.
  이유: 끄는 김에 지우면 진행 중 작업의 증거가 사라진다.
  대신: 지우려면 export로 옮긴 뒤 사용자가 결정한다.
  출처: T-006 §6 (2026-09-22)

- [P-20] **규칙은 결론이다** — 프로젝트 지침과 이 프로토콜이 충돌하면 둘 다 보존하고 사용자에게 보고한다. 규칙을 적용하기 전에 그 [P-nn]의 이유와 대신을 읽는다. 이유·출처 없는 규칙은 결정 기록이나 사용자에게 확인한 뒤 적용한다.
  이유: 결론만 옮겨진 문장은 "이유가 있어야 풀리는 제약"을 절대 제약으로 굳힌다 — 2026-09-23 "훅은 수정하지 않는다"를 "훅을 못 쓴다"로 읽고 설계한 실측.
  대신: 지침 문장에 이유가 없으면 원 결정(T-xxx·날짜)을 연다. 없으면 묻는다.
  출처: T-006 §5 (2026-09-22); 2026-09-23 사용자 "한 줄 고치지 말고 근본 대책"
