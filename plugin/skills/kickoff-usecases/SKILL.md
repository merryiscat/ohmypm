# 킥오프 2부 — 유즈케이스

"무엇을 만드나"에서 "어떻게 굴러가나"로 내려온다. 1부에서 MVP로 남긴 범위만 대상.
산출물은 대상 프로젝트 `docs/usecases.md` — 케이스는 개수 제한 없이 뽑으므로 처음부터 별도 파일로 두고
발굴 중에도 계속 갱신한다.

> **산출물 계약**: `docs/usecases.md` — 케이스 표(해피/배드/필요 기술) + 공통 전제 + 선결 과제, 브라우저 검수 반영.
> **이 절차는 접근법이지 정답 경로가 아니다** — 표를 채우는 것보다 사용자의 실제 장면을 끌어내는 게
> 목적이다. 절차 밖 행동(도메인 조사, 레퍼런스 재확인)이 케이스 품질에 봉사하면 한다.

## 0. 전제

`docs/plan.md`(1부 요약)를 읽고 시작한다(없으면 kickoff-interview부터). `docs/references.md`가 있으면 보기 재료로 쓴다 — 없다고 스윕을 먼저 요구하지 않는다.
usecases.md가 이미 브라우저 검수까지 끝나 있으면 끝낸다.

## 발굴 원칙 — 지어내지 않는다

- **도메인을 모르면 초안을 지어내지 말고 질문으로 이끌어낸다.** 1부 답만으로 케이스가 자명한 영역
  (익숙한 CRUD·대시보드 등)은 초안을 제시해 확인받는 편이 빠르지만, 조금이라도 불확실하면
  **열린 질문으로 사용자가 실제 장면을 말하게 한다** — 지어낸 초안은 한 라운드를 통째로 버린다
  (사용자가 "이거 아니야"만 반복하게 된다). 객관식 보기를 지어내는 것도 같은 함정이다.
- **마일스톤·기능 목록을 유즈케이스로 착각하지 않는다** — 그건 "어떻게 만드나"지 "사용자가 뭘 하나"가 아니다.
- **LLM이 사용자와 상호작용하는 제품은 자명해 보여도 자명하지 않다.** 같은 "이력 입력"도 폼 CRUD일 수도,
  LLM이 주도하는 인터뷰 대화일 수도 있다 — 어느 쪽이냐에 따라 필요 기술이 통째로 갈린다
  (웹 폼 vs 대화 UI+웹 검색+확인 루프). **상호작용 방식(폼인가 대화인가, 누가 주도하나)을 열린 질문으로
  확인하기 전에는** 초안을 제시하지 않는다. (실제 킥오프에서 초안 한 라운드를 통째로 버리게 만든 함정이다.)

## 1. 케이스 발굴 — 하나씩 확정

사용자가 케이스 하나를 던지면 그것을 해피/배드/기술로 끌고 갈 **핵심 갈림길**만 골라 되묻고
(데이터 소스? 자율 범위? 감지 방법? 어디서 멈추나?), 답이 오면 표에 채운 뒤 **그 케이스가 암시하는
다른 케이스**를 되물어 넓힌다(한 케이스의 선택이 새 케이스를 낳는다). 채운 케이스는 채팅에 렌더해
사용자와 같이 보며 고친다.

**유즈케이스는 "누가 / 언제 / 무엇을" 한 줄씩, 최대한 많이 뽑는다** — 개수를 제한하지 않는다.
references.md의 사례를 보기 재료로 쓰되, 사용자에게도 "또 어떤 걸 시키고 싶나"를 계속 던진다.
케이스가 많아 MVP가 커지면 범위는 스택 확정(pl의 T-001 설계 작업)에서 우선순위로 조절하지, 발굴 단계에서 미리 자르지 않는다.

## 2. 케이스마다 채우는 것

| 케이스 | 해피 패스 | 배드 케이스 · 대응 | 필요 기술 |
|--------|-----------|--------------------|-----------|

- **해피 패스** — 문제없이 흘러갈 때를 **구체 장면의 대본**으로 적는다. 대화형 기능이면 시스템과
  사용자가 실제 주고받는 말을 몇 턴 그대로, 화면 기능이면 사용자가 보고 누르는 것을 순서대로.
  **추상 단계(입력 → 처리 → 결과)로 뭉개지 않는다** — 대본에만 드러나는 시스템 행동(검색해서 확인,
  되물어서 구체화, 생성해서 제시)이 곧 필요 기술의 재료다. 끝났다는 걸 무엇으로 아나 — 관찰 가능한
  신호로 적는다("저장됨"이 아니라 "목록에 새 행이 보인다").
- **배드 케이스** — 어긋날 수 있는 지점과 대응. 최소 네 갈래: ① 입력이 잘못됨(빈 값, 형식 위반, 중복)
  ② 외부가 죽음(API 타임아웃·에러, DB 연결 끊김) ③ 권한·한도(인증 만료, 쿼터, 요금) ④ 결과가 비거나
  과함(0건, 너무 많음, 오래 걸림). 각각을 **막을지 / 되돌릴지 / 알리고 넘어갈지** 정한다.
  "에러 처리"로 뭉뚱그리지 않는다 — 어떤 조건에서 사용자가 무엇을 보게 되는지까지.
- **필요 기술** — 그 케이스를 굴리는 데 실제로 드는 것: ① 외부 의존(API·DB·계정·키·쿼터)
  ② 라이브러리·런타임 ③ 해결해야 할 기술 난제(실시간, 대용량, 오프라인, 동시성 등).
  **여기서 스킬·MCP를 적지 않는다** — 도구는 케이스가 아니라 작업 스펙의 '필요 도구'로 정해지고, 워커가 그때 설치한다(kickoff-workspaces PROTOCOL).

케이스를 채우며 같이 관리하는 것:

- **선결 과제** — 아직 없는 필요 기술(계정, API 키, 유료 쿼터, 승인)은 usecases.md 상단에 절로 뽑는다.
  확보 전에는 그 케이스에 착수하지 않는다.
- **공통 전제** — 여러 케이스가 같이 밟는 토대(예: 행동 관찰·학습 인프라, 자율 행동 안전장치).
  케이스별 "필요 기술"을 가로질러 반복되는 항목으로, **하네스·스택은 개별 케이스보다 이걸 보고 고른다** —
  pl의 T-001(스택 확정·design.md) 핵심 재료이자 프로젝트의 진짜 뼈대. usecases.md 상단에 케이스와 분리해 적는다.
- 배드 케이스는 필요 기술을 **늘린다** — 해피 패스만 보면 안 보이던 요구(재시도·백오프, 외부 실패 재현,
  예외 화면 상태, 트랜잭션 롤백)가 여기서 나온다. 이게 2부를 스택 확정 전에 두는 이유다.

## 3. 발굴이 마르면 — 에이전트 제안 라운드

사용자가 더 못 떠올리면 바로 검수로 가지 않는다 — **에이전트가 세 갈래로 후보 케이스를 먼저 제안한다**:

1. **레퍼런스 기반** — `docs/references.md`의 구현체·사례들이 하는 일 중 아직 케이스에 없는 것
2. **보편 기능** — 이 제품 범주라면 사용자들이 당연히 기대할 것 (온보딩, 설정, 알림 관리, 데이터 내보내기 등)
3. **와일드카드** — 일반적이지 않지만 차별화가 될 수 있는 독특한 안건

제안은 케이스당 **한 줄 장면**으로 던진다(기능명이 아니라 "사용자가 ○○하는 장면").
채택된 것만 갈림길 인터뷰로 확정해 표에 올리고, 기각된 것은 사유와 함께 남긴다(필요하면 pending).
발굴 중에도 인접 케이스 제안은 계속하지만, 이 라운드는 **마른 뒤의 마지막 그물**이다 —
사용자 발굴을 대체하지 않는다.

## 4. 전체 목록 브라우저 검수

제안 라운드까지 끝나면, 3부(작업 구조)로 넘어가기 전에 전체 유즈케이스 표를 브라우저로 검수받는다 —
케이스를 개수 제한 없이 뽑으므로 채팅 렌더로는 전체를 한눈에 못 본다.
절차: ① usecases.md 전체(공통 전제·선결 과제 포함)를 **단일 HTML로 렌더** — 임시 위치에 생성,
커밋하지 않는다(단일 출처는 md) ② 그 폴더에서 임시 서버를 백그라운드로 띄우고(`python -m http.server <포트>`)
사용자에게 URL을 준다 ③ 피드백은 **원본 md에 반영**하고 재렌더해 같은 URL에서 재확인 —
HTML만 고치면 확정 후 반영분이 증발한다 ④ 확정되면 서버를 내리고 렌더를 지운다.

## 5. 다음 단계 제안

목록이 확정되면 **선결 과제 목록을 사용자에게 확인시킨다** — 여기서 범위가 조정되면 발굴로 되돌아간다.
확인까지 끝나면 **kickoff-workspaces**(3부 작업 구조 — pl/pl2·구현 워커 워크트리, 첫 설계 작업 T-001로 스택 확정)를 제안한다.
