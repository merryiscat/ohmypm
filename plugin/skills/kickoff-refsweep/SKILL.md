# 킥오프 레퍼런스 수집 — 1부와 2부 사이

2부 케이스를 상상으로 짓지 않도록, 1부 요약을 재료로 **실존 유사 프로젝트·도구·지식·사례**를 먼저 수집한다.
아이디어 수집 단계이므로 **깊이보다 넓이** — 눈덩이식 깊이 탐색이 아니라 매트릭스 병렬 탐색으로 한다.

> **산출물 계약**: 대상 프로젝트 `docs/references.md`(검증·브라우저 검수 반영) + `docs/raw/`에 원시 결과 보존.
> **이 절차는 접근법이지 정답 경로가 아니다** — 워크플로가 놓친 축이 보이면 추가 조사를 하고,
> 수집물이 이미 충분하면 사용자 확인 후 단계를 줄인다.

## 0. 전제

대상 프로젝트 `docs/plan.md`에 1부 요약이 있어야 한다 — 없으면 kickoff-interview부터.
`docs/references.md`가 이미 검수까지 끝나 있으면 끝낸다.

## 1. 기능 분해

1부 요약에서 프로젝트를 기능 4~6개로 쪼갠다 (예: 수집 / 생성 / 발행 / 측정 / 보정). 사용자와 확인한다.

## 2. 스윕 워크플로 실행

**이 스킬 폴더의 `reference-sweep-workflow.js`**를 Workflow로 돌린다 —
args로 projectDef(1부 요약)·functions(기능 분해)·known(기지 노드)을 주입, 인터페이스 상세는 템플릿 상단 주석.

동작: 기능 × 지역(한국·미국·중국·일본 기본) 셀마다 병렬 탐색 에이전트 하나씩 —
지역 언어 쿼리 3~6개를 GitHub·일반 웹·YouTube(지역별 치환: 知乎·Qiita 등)에 돌리고, 깊게 읽지 않고
후보 URL만 최대 8개 수집 → 전체 URL 중복 제거 → 검증 에이전트가 **기능별 쿼터**로
실재·활성·요약 일치를 판정한다 (updated_at 메타데이터를 커밋으로 오독하는 게 흔한 함정).
drop은 **사유와 함께** 기록한다 — 재검토 방지.

## 3. 병합

keep만 대상 프로젝트 `docs/references.md`에 기능별로 병합하고, 원시 결과 전문은 `docs/raw/`에 불변 보존한다.
검증 상한에 잘린 미검증분은 하이라이트만 발췌하고 잘렸음을 명시한다.

## 4. 브라우저 검수

병합으로 끝내지 않는다 — 통계 요약("keep 24건 병합")만 채팅에 남기면 사용자는 수집물을 실제로
본 적이 없는 채 2부에 들어간다. 보기 재료로 쓰라고 모은 것이므로 반드시 훑게 한다.

절차: ① references.md 전체를 **단일 HTML로 렌더** — 임시 위치에 생성, 커밋하지 않는다(단일 출처는 md)
② 그 폴더에서 임시 서버를 백그라운드로 띄우고(`python -m http.server <포트>`) 사용자에게 URL을 준다
③ 피드백은 **원본 md에 반영**하고 재렌더해 같은 URL에서 재확인 — HTML만 고치면 확정 후 반영분이 증발한다
④ 확정되면 서버를 내리고 렌더를 지운다. 남는 것은 갱신된 md뿐이다.
페이지 구성: 기능별 keep 표(이름·클릭 가능한 링크·kind·지역·요약·활성 신호)를 본문으로,
drop(사유 포함)과 미검증분은 접힌 절로 — 잘린 것도 사용자가 펼쳐 구제할 수 있어야 한다.
피드백 반영: 버릴 것은 지우고, 더 파고 싶은 노드는 **미확장 노드**로 표시해 둔다(3부 이후 깊이 탐색 후보).

## 5. 다음 단계 제안

검수 피드백이 references.md에 반영되면 끝. 케이스 발굴이 필요하면 kickoff-usecases를 제안만 한다 — 기본 경로가 아니다.
레퍼런스는 2부에서 두 가지로 쓴다: 케이스 발굴의 **보기 재료**(이런 걸 남들은 시킨다), 필요 기술 열의
**선행 구현체**(이미 있는 걸 발명하지 않기). 사용자의 실제 장면을 대체하지는 않는다 — 열린 질문 원칙은 그대로다.
