# 킥오프 1부 — 프로젝트 성격

킥오프는 짧다: **kickoff-interview → kickoff-workspaces**(작업 구조) — 10분짜리 기계적 세팅이다.
레퍼런스 스윕(kickoff-refsweep)·유즈케이스(kickoff-usecases)는 **선택**이다: 생각하는 일은 구조가 깔린 뒤 pl의 몫이고,
pl이 스펙의 '필요 도구'로 요구할 때 main에서 돌린다. (2026-09-17 축소 — 20개 프로젝트에서 앞단 문서는 쌓였는데 설계로 이어진 게 0이었다)
층 구조가 뼈대다: **케이스(목표) → 스택(수단) → 도구** — 선택은 이 방향으로만 흐른다.
1부에서 나오는 스택은 가설이다. 스택 확정은 3부가 연 pl의 첫 설계 작업(T-001)이 하고, **도구는 작업 스펙이 요구하기 전에는 아무것도 설치하지 않는다.**

> **산출물 계약**: 대상 프로젝트 `docs/plan.md`에 1부 요약 한 문단(+미확정 질문), 워크스페이스 생성·첫 커밋.
> **이 절차는 접근법이지 정답 경로가 아니다** — 사용자·대상의 실제 사정과 충돌하면 그쪽이 이기고,
> 절차에 없는 행동(추가 질문·조사)이 산출물 품질에 봉사하면 주저 없이 한다.

## 0. 어디까지 왔나

대상 프로젝트가 이미 있고 `docs/plan.md`에 1부 요약이 있으면 1부는 끝난 것이다 —
plan.md에 미확정 질문이 남아 있으면 그것만 마저 묻고, 아니면 바로 3(다음 단계 제안)으로 간다.

## 1. 인터뷰

AskUserQuestion으로 단계별로 묻는다. 이미 답이 나온 단계는 건너뛰고, 프로젝트 유형이 판별될 때까지 진행한다.

1. **문제·목적** — 무엇을 해결하나? 완성되면 뭐가 달라지나(성공 기준)?
2. **산출물 형태** — 코드인가, 문서인가, 화면인가, 콘텐츠(글·영상)인가
3. **스택** — Python / 순수 HTML / React·Next / 모바일(Expo·Flutter) / 데스크톱 / 데이터 분석 / 해당 없음
4. **화면** — 있다면 와이어프레임부터인가, 바로 스타일 입히는가
5. **외부 연동·배포** — DB(Supabase?), 알림(Telegram?), 웹 배포, 파일 산출물(Word/Excel), API 연동
6. **범위** — MVP에 꼭 들어갈 것 vs 나중으로 미룰 것

완료 기준: 여섯 항목이 채워져 **1부 요약 한 문단**(뒤 단계들이 projectDef로 쓴다)을 쓸 수 있다.
이 스택은 가설일 뿐이다 — 케이스를 훑기 전의 스택은 대개 항목이 빠져 있고, 그 위에서 고른 도구는 과하거나 모자란다.

## 2. 대상 워크스페이스 생성

레퍼런스 수집·2부보다 먼저 워크스페이스를 판다:

1. 프로젝트 이름을 사용자와 정한다
2. 프로젝트 폴더 생성(위치·이름은 사용자 관례를 따른다) + `git init`
3. **llmwiki 스킬로 init** (이 팩에 동봉된 스킬) — docs/ 위키 스키마와 훅까지 설치.
   llmwiki가 설치돼 있지 않으면 `docs/` 폴더만 만들고 다음으로 간다
4. 1부 요약을 그곳 `docs/plan.md` 초안으로 첫 커밋. 미확정 질문도 plan.md에 남긴다 —
   세션이 끊겨도 대상 프로젝트에서 인터뷰를 이어갈 수 있다

위키를 이 시점에 여는 이유: 이후 레퍼런스 수집·2부 산출물이 처음부터 위키 페이지(index·log 등재)로
들어가고, 세션이 중간에 끊겨도 훅·인덱스 없는 반쪽 docs가 남지 않는다.
이후 모든 산출물과 진행 기록은 그 저장소로 간다 — **플러그인 폴더에는 아무것도 남기지 않는다**
(ohmypm 플러그인은 절차이지 프로젝트 기록처가 아니다).

## 3. 다음 단계 제안

plan.md 첫 커밋까지 끝나면 **kickoff-workspaces**(작업 구조)를 제안한다. 선례가 많은 영역이거나 사용자가
장면을 먼저 뽑고 싶어 하면 그 전에 kickoff-refsweep·kickoff-usecases를 **제안만** 한다 — 기본 경로가 아니다.
