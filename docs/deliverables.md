# 산출물 대장

PM이 각 프로젝트의 **단계를 판단하고, 그 단계에 빠진 산출물을 요구**할 때 쓰는 기준표.
(2026-09-08 사용자 확정. 이 문서는 규약 성격이라 상시 유지한다 — 반영 후 삭제 대상이 아니다.)

## 산출물의 자격

- **PM이 열어볼 수 있어야 한다** — 파일 경로로 지목되는 것만 산출물이다.
  "합의했다"·"머릿속에 있다"는 산출물이 아니다.
- **하나의 산출물 = 하나의 파일**. 여러 파일에 흩어지면 판정이 흐려진다(`screens/*.html`처럼 묶음은 예외).
- **없는 게 곧 나쁨은 아니다** — 그 프로젝트의 현재 단계 것만 요구한다. 뒤 단계 산출물은 안 묻는다.

## 단계

기획 → 설계 → 구축 → 검증 → **운영**. 궤도 밖 상태가 둘 있다: **중단**, **보관**.

- 운영을 다섯 번째로 둔 이유: 이미 매일 도는 것(ohmyPM·project_odin·naverblog)은 만드는 중이 아니다.
  테스트로 끝나는 사다리면 이것들이 갈 칸이 없다.
- 외부에서 받아온 저장소·보관용(CrisperWhisper_merry·marker·orca·claudedocs 등)은 **단계를 매기지 않는다**.
  온보딩 분류('외부 클론 / 보관용 / 내 프로젝트')를 그대로 쓴다. 여기에 산출물을 요구하면 소음이다.

## 기획 — 무엇을 왜 만드는가

| 산출물 | 경로 | 조건 |
|---|---|---|
| 기획서 | `docs/plan.md` | 필수 |
| 유즈케이스 | `docs/usecases.md` | 필수 |
| 레퍼런스 검수 | `docs/references.md` | 선례가 있는 영역만 |
| 위키 골격 | `docs/index.md` + `docs/status.md` | 필수 |

킥오프 체인(인터뷰 → 레퍼런스 → 유즈케이스 → 하네스)이 이미 만들어내는 것들이다. 새로 정의하지 않고 그대로 쓴다.

## 설계 — 어떻게 생겼는가

| 산출물 | 경로 | 조건 |
|---|---|---|
| 구성 한 장 | `docs/design.md` | 필수 |
| 인터페이스 계약 | `docs/interfaces.md` | 대외 API를 내놓거나 외부 서비스를 쓰면 |
| 화면 설계 | `screens/*.html` | 사람이 보는 화면이 있으면 |
| 데이터 구조 | 스키마 파일(코드 안) | 데이터를 저장하면 |
| 외부 연동 키 목록 | `.env.example` | 외부 서비스·키를 쓰면 |

**`docs/design.md`** — 무엇이 무엇을 부르고 데이터가 어디로 흐르는지. **한 장 분량 상한**(길면 부담이 되어 안 쓰게 된다).

**`docs/interfaces.md`** — 두 절로 나눈다.
- *내놓는 것*: 엔드포인트, 용도 한 줄, 입출력, 인증 여부
- *쓰는 것*: 서비스, 용도, 대응하는 `.env` 키 이름, 한도·비용, 만료·갱신 주의

`design.md`와 합치지 않는 이유: 구성은 큰 개편 전까지 안 바뀌는데 인터페이스는 엔드포인트가 늘 때마다 바뀐다.
수명이 다른 둘을 한 파일에 두면 어느 절이 낡았는지 판정이 안 된다.
덤으로 FastAPI 프로젝트는 `/openapi.json`이 자동 생성되므로 **PM이 문서와 실제 코드를 기계 대조**할 수 있다 —
존재만이 아니라 정확성까지 검증되는 드문 산출물이다.

*'쓰는 것' 절이 필요한 이유(실증)*: `.env.example`은 키 이름만 준다. 무슨 용도로 어떤 한도·만료 조건에서 쓰는지는
어디에도 없었고, 그래서 구글 OAuth 테스트 모드의 리프레시 토큰 7일 만료 같은 함정을 코드로는 알 수 없었다(2026-09-08 글로벌 지침).

## 구축 — 돌아가는가

| 산출물 | 경로 | 조건 |
|---|---|---|
| 실행 절차 | `README.md` 또는 `docs/setup.md`의 실행 명령 | 필수 |
| 의존성 잠금 | `uv.lock` / `package-lock.json` 등 | 코드 프로젝트면 |
| 비밀키 차단 | `.gitignore`에 `.env` + 실제로 커밋 안 됨 | 필수 |

마지막 항목만 문서가 아니라 점검이다. 넣은 이유는 **되돌릴 수 없는 사고**이기 때문 — 키가 한 번 올라가면 지워도 늦다.

## 검증 — 맞다는 근거가 있는가

| 산출물 | 경로 | 조건 |
|---|---|---|
| 자동 테스트 | `tests/` | 있으면 |
| 검증 기록 | `docs/log.md`의 "검증:" 줄 | 필수 |
| 실패 항체 | `docs/mistakes.md` | 사고가 났으면 |

자동 테스트를 필수로 걸면 거의 전 프로젝트가 미충족이 된다(내 프로젝트 중 `tests/`가 있는 건 project_odin 하나).
대신 **무엇을 어떻게 확인했는지 기록**을 필수로 삼는다. 이미 쓰는 형식이다.

## 운영 — 내일도 도는가

| 산출물 | 경로 | 조건 |
|---|---|---|
| 다른 PC 재현 절차 | `docs/setup.md` | 상시 도는 것이면 |
| 실행 등록 | ohmyPM 포트 레지스트리·스케줄 등록 여부 | 서버·상시 실행이면 |
| 실패 알림 | 알림 경로가 붙어 있는지 | 무인 실행이면 |

---

## 판정은 두 단계

1. **존재** — 파일이 있는지는 코드가 센다(스캔).
2. **내용** — 실제로 그 역할을 하는지는 PM이 열어보고 판단한다. 빈 `design.md`나 제목만 있는 `plan.md`는 통과시키지 않는다.

판정 에이전트·이슈 완결 검증에서 이미 쓰는 방식(결정론 수집 + LLM 판단)을 그대로 재사용한다.

## 착수 시점의 현황 (2026-09-08 스냅샷)

내 프로젝트 20개 남짓 기준. 이 숫자가 곧 요구가 몰릴 곳이다.

| 산출물 | 가진 프로젝트 |
|---|---|
| `docs/plan.md` | 12 |
| `docs/usecases.md` | 9 |
| `docs/references.md` | 8 |
| `docs/index.md`(위키) | 13 |
| `.env.example` | 8 |
| `screens/` | 3 (n_step, ohmyPM, project_odin) |
| 스키마 파일 | 3 |
| `tests/` | 1 (project_odin — 나머지는 외부 클론의 것) |
| **`docs/design.md`** | **0** |
| **`docs/interfaces.md`** | **0** |
| **`docs/setup.md`** | **1 (ohmyPM만)** |

가장 큰 공백 둘: **구성·인터페이스 문서가 전무**하고, **재현 절차가 ohmyPM에만** 있다.
후자는 PC가 바뀌거나 디스크가 죽으면 나머지를 되살릴 수 없다는 뜻이다.

## 미확정 — 요구를 어디로 내보낼지

제안: **칸반 이슈로 띄우되 프로젝트당 동시에 하나만**(현재 단계에서 빠진 것 중 가장 앞의 하나).
전부 걸면 프로젝트 20개 × 산출물 15종이라 카드가 백 장 넘게 쏟아지고, 그러면 아무도 안 본다.
→ 확정 전까지 배선하지 않는다.
