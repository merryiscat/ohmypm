# T-005 사용자와 함께 완성하는 설계 루프와 측정

- 상태: 검토 반영 v2
- 등급: L — 설계·검토 절차와 모델 선택 구조 변경
- 작성: pl, 2026-09-19
- **요청 원문**:

> pl 에게 되묻게 하는게 맞지 않을까?
>
> pl 이 코드를 안 읽는다고???그러면 예를 들면 버튼을 고치라는 요청이 들어오면 pl은 어떻게 고쳐?
>
> 이때 말한 병목은 작업 들어가서 에이전트가 요청하는 사항이 있는데 아무도 신경 안쓰는 상황이라 그냥 하염없이 멈춘거고, 설계 기획은 시간과 토큰을 얼마를 들이든 부족하지.
>
> 모델 배치 pl과 pl2 그리고 나의 합작품을 통해 작업계획서를 최고 프론티어 모델들을 통해 완성시키고 싶은거임. 내 처음 기획은 main 은 머지용이였어
>
> 이거를 하드코딩하는게 아니라 모델 확인 후 최상위 모델은 한도가 있으니 소진시 다음 모델을 사용할 수 있게 해야하지 않겠나? 당장 이틀 후면 페이블 소진 한도가 돌아올텐데?
>
> 지금 odin_3.0 에 매매모델을 개발하는 것으로 벤치마크를 잡아보자. 어차피 여러개의 매매모델이 필요하고, 벤치마크 기준으로 삼아보자.
>
> 그리고 작업을 진행하는 파이프라인에서 생기는 서로 주고 받는 작업계획서 데이터들은 로그파일로 그대로 남겨서 어떤 값들을 주고받는지 체크해서 토큰상의 병목들을 측정할수 있게해두자

## 목표
pl·pl2·사용자가 가용 최상위 모델로 작업계획서를 완성하고, 방치된 요청과 토큰 병목을 odin_3.0 벤치마크에서 확인할 수 있게 한다.

## 범위
- 안: 설계 문답·코드 열람 규칙, 미응답 처리, 모델 가용성에 따른 선택, 원문 로그와 벤치마크 측정 준비.
- 검토: 내용이 같은 산출물의 재검토만 금지하며, 실제 내용이 바뀐 v2·v3는 새 대상이다. `PROTOCOL.md` 4절을 이에 맞추고 근거절은 유지한다.
- 벤치마크: odin_3.0 매매모델 1호 바퀴로 문답·열람을 확인한다. 여러 과제의 단계별 토큰·대기시간 비교 절차는 플러그인 템플릿에, 원문 로그·실측 데이터는 프로젝트 로컬에 둔다.
- 밖: main을 머지 전담으로 변경(벤치마크 수치 확인 후 다음 판 결정), 매매모델 자체 설계·구현.

## 완료 기준 (관찰 가능한 문장 — 기준 하나에 확인 방법 하나)
1. [ ] 설계 질문이 pl에 돌아와 사용자 답변과 pl2 지적을 반영한 작업계획서로 이어진다 — 확인: odin_3.0 매매모델 1호 바퀴에서 pl이 실제로 되물은 기록과 반영본을 대조한다.
2. [ ] pl이 대상 코드를 읽고 파일·현재 동작을 근거로 스펙을 쓴다 — 확인: odin_3.0 매매모델 1호 바퀴의 실제 코드 열람 기록과 스펙 근거를 대조한다.
3. [ ] 설계 루프는 고정 시간·토큰·버전 횟수 상한 없이 미해결 쟁점 해소와 사용자 승인으로 종료한다 — 확인: 갱신된 절차·역할·프롬프트의 종료 조건을 대조한다.
4. [ ] 응답 없는 에이전트 요청은 중계자인 main이 재확인 주기·적재 큐 없이 즉시 사용자에게 올린다 — 확인: 미응답 요청 한 건의 인지 직후 사용자 보고 기록을 확인한다.
5. [ ] 매 태스크에서 main이 `docs/roles.md`의 벤더별 최상위부터 호출하여 소진 응답이면 같은 벤더의 다음 모델을 선택한다(pl=Codex, pl2=Claude) — 확인: 정상·연속 소진·회복 후 다음 태스크의 호출/응답 기록을 대조한다.
6. [ ] 파이프라인이 주고받은 작업계획서·질문·답변·검토 원문을 송수신 순서대로 로그파일에서 복원할 수 있다 — 확인: 한 문답의 실제 전달 내용과 로그를 대조한다.
7. [ ] 단계별 토큰·대기시간 집계에 태스크 종료 시 `/status`로 수집한 pl 실측 토큰이 들어간다(정액제 pl2·main만 미측정 허용, 전 단계 미측정은 실패) — 확인: 로그 집계를 `/status` 원본·시각 기록과 대조한다.
8. [ ] 플러그인 변경이 이 저장소 복사본(`docs/protocol.md`·`docs/roles.md`·`CLAUDE.md`·`AGENTS.md`)까지 반영된다 — 확인: 갱신 후 복사본의 설계·열람·모델 규칙을 플러그인 원본과 대조한다.

## 손대는 파일
- `plugin/skills/kickoff-workspaces/` 아래 `PROTOCOL.md`, `templates/{task,review,roles,prompt-pl,prompt-pl2}.md`, `templates/{AGENTS,CLAUDE}.md.block` — 설계 루프·변경본 검토·열람·벤더 고정 규칙.
- 같은 스킬의 `scripts/{ws-model,ws-upgrade}.sh` — 수동 2단 스위치 폐기·태스크마다 최상위 재시도·복사본 갱신; 모델명·우선순위 단일 출처는 각 프로젝트 `docs/roles.md`.
- `plugin/skills/dispatch/SKILL.md` — main의 호출 응답 기반 전환·즉시 보고·원문 로그·`/status` 수집과 집계(Claude 자동 하향에 의존하지 않음).
- `plugin/skills/kickoff-workspaces/templates/benchmark.md` — 커밋되는 비교 절차; 각 프로젝트 `docs/benchmark.md`는 로컬 전용 실측 기록처로 유지.
- 이 저장소 `docs/protocol.md`, `docs/roles.md`, `docs/{tasks,reviews}/_template.md`, `AGENTS.md`, `CLAUDE.md` — main이 원본 변경을 반영.

## 검증 (pl2, 구현 후)

**0. 요청 대조** — `대조: 일치 — 다만 원문이 요구한 odin_3.0 벤치마크는 절차만 놓였고 바퀴는 돌지 않았다.`
원문의 "되묻게"는 `AGENTS.md`·`prompt-pl.md`·protocol 3절의 되묻기 규칙으로, "코드를 안 읽는다고"는 코드 읽기 허용으로,
"시간과 토큰을 얼마를 들이든"은 왕복 상한 폐지로, "아무도 신경 안쓰는 상황"은 즉시 보고(주기·큐 없음)로,
"하드코딩하는게 아니라 모델 확인 후"는 벤더별 우선순위와 `ws-model.sh` 폐기로, 마지막 문장은 `pipeline-log.py`로 각각 대응한다.
원문에 없는 산출물이 새로 들어온 것은 없다.

| 기준 | 판정 | 확인한 방법 |
|---|---|---|
| 1 설계 질문이 pl에 돌아와 반영본으로 이어진다 | 실패 | 확인 방법이 스펙상 odin_3.0 매매모델 1호 바퀴인데 **그 바퀴가 아직 돌지 않았다** — 대조할 되물음 기록도 반영본도 없다. 규칙이 문서에 들어간 것은 확인했으나(`PROTOCOL.md` 2·3절, `templates/prompt-pl.md`, `templates/AGENTS.md.block`) 그것은 스펙이 정한 확인 방법이 아니다. main에 돌린다 — 1호 바퀴를 돌린 뒤 이 칸만 다시 판정하면 된다 |
| 2 pl이 대상 코드를 읽고 근거로 스펙을 쓴다 | 실패 | 기준 1과 같은 이유로 대조 대상이 없다. 금지 문구가 걷혔고 읽기 허용이 들어간 것은 `PROTOCOL.md` 3절·`templates/AGENTS.md.block`·`templates/roles.md`에서 확인했으나, 실제 열람 기록은 존재하지 않는다 |
| 3 설계 루프는 상한 없이 쟁점 해소와 사용자 승인으로 종료 | 통과 | 네 곳의 종료 조건을 서로 대조했다. `PROTOCOL.md` 2절("왕복에는 횟수 상한이 없다 … 끝내는 것은 소진이 아니라 미해결 쟁점이 없어지고 사용자가 승인하는 것"), 0절의 규칙 셋 철회 문단, `templates/roles.md` 난이도 등급표 머리의 "설계에는 시간·토큰 상한을 두지 않는다", `templates/prompt-pl.md`의 "왕복 횟수에 상한은 없다". 네 곳이 서로 어긋나지 않는다 |
| 4 미응답 요청은 main이 주기·큐 없이 즉시 사용자에게 | 통과 | 규칙은 `PROTOCOL.md` 7절·`templates/CLAUDE.md.block`·`dispatch/SKILL.md`에 있고, 저장소 전체를 훑어 재확인 주기나 적재 큐를 남긴 조항이 없음을 확인했다(과거 로그의 서술만 남는다). 실물 기록으로는 pl2가 올린 차단 지적 중 결정이 필요한 것들을 main이 v2 지시 전에 사용자에게 올려 답을 실어 보낸 건이 남아 있다 — 지시서 본문의 "사용자 결정" 항목과 스펙 `검토 반영` 표의 "사용자 확정" 처리로 대조했다. 다만 이 바퀴의 로그는 소급 기록이라 "직후"를 시각으로는 입증하지 못하고 파일 내용으로만 확인했다 |
| 5 벤더별 최상위부터 호출, 소진 응답이면 같은 벤더의 다음 | 실패 | **앞서 지적한 증거처 부재는 해소됐다** — 로거의 send·recv·usage·note 네 하위 명령 모두 `--model`을 받고, 기록에 모델 칸이 생겼으며, `report` 표에 모델 열과 방향별 "실제로 돈 모델" 줄이 나오고 한 건도 없으면 경고가 울린다. 실제 기록도 확인했다 — 집계 열한 건 중 최근 두 건에 실제 응답 모델이 남아 있다. 그럼에도 **통과로 쓰지 않는 이유는 둘**이다. (가) 확인 방법이 요구한 전이 셋 가운데 정상 하나만 기록됐고 연속 소진과 회복 후 다음 태스크는 아직 일어나지 않아 대조할 것이 없다. (나) 정작 한도가 차서 내려갈 자리인 pl 쪽 기록이 비어 있게 되어 있다 — `dispatch/SKILL.md`에서 pl 산출물을 받는 `recv` 예시와 결산 `usage` 예시에는 `--model`이 붙어 있지 않고(pl2 쪽 두 줄에는 붙어 있다), `report`의 경고는 모델이 **한 건도** 없을 때만 울리므로 main 행만 기록돼도 조용히 지나간다. 판정 근거는 이 워크트리 사본이 아니라 커밋된 최신 내용과 실제 집계 출력으로 대조했다 |
| 6 주고받은 원문을 순서대로 로그에서 복원 | 통과 | 한 문답이 아니라 이번 바퀴에 오간 파일 여섯 건 전부를 로그의 원문 칸과 **글자 단위로 비교해 모두 완전 일치**를 확인했다(스펙 v1 지시·스펙·검토 지시·검토서·v2 지시·산출물 검토 지시). 순서는 왕복 번호로 복원된다. 다만 로그 첫 건이 스스로 밝히듯 이 바퀴의 스펙 v1 원문은 v2에 덮여 남지 않았다 — 그것을 막는 장치(보내기가 로그를 먼저 쓴다)는 들어갔으나 이 바퀴에는 소급 적용이라 걸리지 않았다 |
| 7 집계에 `/status` pl 실측 토큰이 들어간다 | 통과 | 로그의 사용량 건에 `/status`가 찍은 줄이 원문 그대로 보존돼 있고, 파싱된 합계·입력·캐시입력·출력이 그 줄과 맞는지 직접 계산해 대조했다(합계 = 입력 + 출력). `report` 출력에 단계별 토큰 칸과 직전 기록으로부터의 간격 칸이 모두 나오고, 정액제 자리만 미측정으로 표시되며 전 단계 미측정이 아니다. 다만 이 바퀴는 소급 기록이라 중간 항목의 간격은 실제 송수신 간격이 아니다 — 로그 첫 건이 그 사실을 적어 두었다 |
| 8 플러그인 변경이 이 저장소 복사본까지 반영 | 통과 | 네 복사본을 원본과 직접 비교했다. `docs/protocol.md`는 플러그인 `PROTOCOL.md`와 설치 표시 주석 한 줄을 빼고 완전 일치, `docs/roles.md`는 `templates/roles.md`와 완전 일치, `CLAUDE.md`·`AGENTS.md`의 작업 구조 블록은 각 `.block` 파일과 글자 그대로 같고 버전 표시가 0.8.0이다. 두 `_template.md`도 같은 방식으로 일치를 확인했다 |
