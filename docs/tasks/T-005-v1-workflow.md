## 목표·범위
기존 요청→설계→구현→검증 흐름을 main 접수·운영 / pl 설계·품질 책임 / work 구현으로 재구성해 요구사항 누락과 구현 결함을 줄인다. Orca·Git 프로젝트를 대상으로 ohmypm부터 적용한다. 기존 점검·보고 기능은 보존하고 통합·새 화면·원격 푸시·배포는 제외한다. 사용자 예외 승인으로 이번 세션에서 구현과 검증을 이어간다.

## 합의한 설계
- **main**: 요청 접수, 작은 가역 수정 직접 처리, pl 연결, 사용자 알림, 환경 준비·회수, 통과한 변경의 로컬 머지. 설계가 필요해지면 직접 처리를 중단하고 pl로 연결한다.
- **pl**: 최고 성능 모델을 배치하고 사용자와 필요한 만큼 기획·설계·추론한다. 완료 기준·시나리오·검증 방법·작업 분해·하네스를 함께 합의한다. 1.0 전환 후 코드 열람·work 환경의 동작 검증을 허용하며, 구현 수정은 work에 돌린다. 상시 pl2는 두지 않는다.
- **사용자 대화**: pl이 판단 요청을 main에 보내면 main이 pl 대화와 질문 위치를 안내한다. 실제 논의는 사용자↔pl이며, 특정 설계 버전의 구현 요청을 받아야 실행한다. 기준 변경은 재합의하고 이전 버전의 승인·판정은 새 버전에 적용하지 않는다.
- **work**: 승인된 범위만 구현·검증해 변경과 실행 근거를 제출한다. pl은 기준별 통과/실패를 판정하고 실패는 work에 돌린다. 미실행 검증은 통과로 기록하지 않는다. 합의된 기준을 work가 낮추거나 삭제할 수 없다.
- **작업 컨테이너**: Orca 워크트리·브랜치·독립 세션·특화 하네스·실행 설정의 묶음이다. Docker 필수 또는 OS 보안 격리를 뜻하지 않는다. 기존 스킬·MCP·의존성·검증 도구를 우선 조합하고 필요한 확장은 설계 합의에 포함한다. 의존성·환경변수·포트·테스트 데이터의 충돌을 필요한 작업에서 분리하며 공용 설정을 임의 변경하지 않는다. 준비 확인에 실패하면 work를 시작하지 않는다.
- **병렬**: pl이 수정 영역·의존성·검증 독립성·실행 자원 충돌을 확인한 작업만 최대 두 work로 병렬 실행한다. 상대의 미완성 변경 없이 구현·검증할 수 없거나 독립성이 불명확하면 순차 실행한다. main의 머지는 항상 순차다.
- **전달 계약**: 파일에 요청 원문·사용자 결정·버전별 스펙·하네스 구성·결과를 보존한다. 알림 필드는 `작업 ID / 설계 버전 / 이벤트 종류 / 자료 위치`이며 알림 자체를 승인으로 간주하지 않는다. main이 실행 상태, pl이 설계·품질 판정을 소유한다. 중단·중복 알림 후에는 기존 상태와 실제 work·커밋을 대조해 재개하고 중복 실행·머지를 막는다.
- **통합·회수**: pl의 통과 판정은 `설계 버전 / 결과 커밋 / 통합 기준 커밋`에 연결한다. main이나 결과가 바뀌면 최신 기준의 통합 후보를 work 환경에서 재검증하고 pl의 판정을 갱신한다. 의미 판단이 필요한 충돌은 work·pl로 돌린다. main은 판정된 통합 커밋으로 로컬 머지하고 알린다. 머지·결과 보존이 확인된 환경만 회수하며, 실패·미반영 변경·사용자 변경은 보존한다.

## 완료 기준 — 항목별 확인 하나
1. [x] 단순 요청은 pl·work 생성 없이 main에서 완료된다. — 확인: dispatch 직접 처리 분기와 아래 확인 범위 참조.
2. [x] pl 질문 알림부터 다회 사용자 논의와 해당 설계 버전의 구현 승인까지 이어진다. — 확인: 두 차례 설계 수정·이벤트·승인 시나리오.
3. [x] work는 승인된 하네스의 준비 확인을 통과한 작업 환경에서 실행된다. — 확인: 정상 구성·도구 누락·자원 충돌·공유 의존성 거부.
4. [x] 독립 작업은 최대 두 개 병렬, 의존·충돌·불명확 작업은 순차로 진행된다. — 확인: 프로젝트 전체 활성 작업의 일정 검사.
5. [x] pl이 코드·실제 동작을 확인하고 합의한 기준별 판정·근거를 남긴다. — 확인: 실패→수정→통과 테스트 및 실제 work 보고서의 diff·check·verdict.
6. [x] 실패하거나 설계·결과·통합 기준이 달라져 판정이 낡은 변경은 머지되지 않는다. — 확인: 실패·참조 변경·재검증 중단에 대한 통합 거부.
7. [x] 중단·중복 알림 뒤 기존 변경을 보존하고 같은 작업을 중복 생성·머지하지 않는다. — 확인: 생성·실행·전달·머지·회수 중단 복구.
8. [x] ohmypm의 새 작업부터 검증된 변경이 로컬 머지되고 결과 보존 후 환경이 회수된다. — 확인: 실제 Orca 작업 T-005-SMOKE/T-005-LIVE 모두 done/cleaned.

## 구현 대상·필요 도구
- main 구현 대상: 기존 ohmypm 플러그인의 작업 구조 원본·설치/갱신 절차·역할별 지침·템플릿·Orca 연동. 프로젝트 복사본만 고치지 않는다. 원본과 복사본을 함께 1.0.0으로 맞추고 기존 설정·진행 중 작업을 보존한다.
- 착수 확인: main이 설치된 Orca의 워크트리·터미널·알림 기능을 먼저 확인한다. 사용 도구는 Orca CLI·Git·역할별 모델 CLI와 합의한 하네스 구성이다. 명령·경로는 설치본에서 확인하며 미지원 기능을 작동한다고 가정하지 않는다.
- 확대 조건: ohmypm에서 대표 작업을 같은 도구·완료 기준·비슷한 예산의 강한 단일 모델과 반복 비교해 누락·결함·사용자 수정 횟수·시간·비용을 기록한다. 사용자가 결과를 확인한 뒤 선택한 프로젝트로 확대한다. 별도 벤치마크 서비스는 만들지 않는다.

## 검토 반영 (v2)
별도 pl2 검토서는 없다. 기존 문서는 목적·운영 제약을 참고했으며, 새 work 금지·pl 문서 전용·상시 pl2 규칙은 1.0의 역할 설계에 계승하지 않는다. 이번 1.0 구현에는 사용자가 승인한 일회 예외를 적용했다.
