## 1. 목표와 불변 조건

ohmyPM을 설치·갱신·해제해도 대상 프로젝트의 추적 파일, index, HEAD는 기본적으로 바뀌지 않는다. 하네스 제공을 위해 프로젝트 커밋을 요구하지 않는다. 제품 코드·제품 설계·프로젝트 고유 개발 규칙은 프로젝트가 소유하고, 에이전트 운영 도구·역할·모델·실행 상태는 작업 환경이 소유한다.

프로젝트별로 값이 다르다는 이유만으로 프로젝트 파일에 저장하지 않는다. 프로젝트 경로에 로컬 파일이 필요하더라도 그것은 생성된 전달물이며 원본이 아니다. 프로젝트의 빌드·테스트 의존성까지 외부 환경으로 옮기지는 않는다.

예외는 기존 1.0 설치 흔적을 제거하는 일회성 전환이다. 추적 파일의 제거는 명시적인 프로젝트 변경이며 일반 환경 설치와 별도로 검토·커밋한다. 과거 이력을 재작성하거나 자동으로 푸시하지 않는다.

## 2. 현재 구현에서 확인한 결합

- `plugin/skills/kickoff-workspaces/scripts/ws_upgrade.py`: 실행기·공통 문서·템플릿·훅을 프로젝트로 복사하고 AGENTS.md/CLAUDE.md 및 .gitignore를 수정한다.
- `plugin/skills/dispatch/scripts/workflow_core.py`: 모델 기본값을 프로젝트 `docs/workflow.json`에서 읽는다. 상태는 Git 공통 디렉터리 `ohmypm-v1/`에 보존한다.
- 같은 실행기의 `prepare_harness`: 워크트리에 context와 overlay를 만들고 공통 `info/exclude`를 수정한다.
- `launch`: context 내용과 실행기 경로를 실행 요청에 전달한다. 따라서 지침 전달을 프로젝트 지침 파일 수정과 분리할 출발점이 있다. 모든 역할·모델에서 실제로 읽히는지는 아직 검증하지 않았다.
- 기존 pre-commit 훅은 브랜치 이름으로 pl의 docs 밖 커밋을 막는다. 프로젝트 훅 소유권과 역할 정책이 결합되어 있다.

## 3. 소유권과 저장 위치

| 자산 | 소유자 | 저장·배포 계약 |
|---|---|---|
| 제품 코드, 빌드·테스트 설정, 프로젝트 고유 AGENTS.md/CLAUDE.md | 프로젝트 | 기존 Git 정책 유지 |
| 제품 요구사항·설계·유지보수에 필요한 결정 | 프로젝트 | 프로젝트가 선택한 문서 위치에 명시적으로 반영 |
| 실행기, 역할·절차, 공통 템플릿, adapter | ohmyPM | 플러그인 원본 및 외부의 불변 버전 패키지 |
| 역할별 모델, 프로젝트별 환경 선택, 로컬 도구 위치 | 로컬 작업 환경 | Git 공통 디렉터리 `ohmypm/`의 프로젝트 설정 |
| 원문, 승인, 운영 스펙, manifest, 판정·실행 증거 | 로컬 작업 환경 | 같은 디렉터리의 작업별 버전 기록 |
| 임시 context·설정 전달물 | 로컬 작업 환경 | 외부 세션 디렉터리 우선, 필요한 경우에만 미추적 로컬 전달물 |

ohmyPM 자체 저장소의 `plugin/`은 제품 소스이므로 계속 커밋한다. 이 T-006도 ohmyPM 제품의 설계 문서다. 반면 소비 프로젝트마다 설치본을 복사하고 커밋하지 않는다.

기본 로컬 상태 루트는 `git rev-parse --path-format=absolute --git-common-dir`로 찾은 공통 디렉터리 아래 `ohmypm/`이다. `.git`이 파일인 워크트리도 같은 상태를 찾는다. Git 메타데이터 사용은 허용하되 Git 전송 대상에는 포함하지 않는다. 기존 `ohmypm-v1/`는 호환 영역으로 남긴다.

외부 런타임 저장소는 사용자별 ohmyPM 데이터 디렉터리이며, 명시적 경로 override를 지원한다. OS 기본 위치와 override 우선순위는 구현 문서·doctor 출력으로 고정한다. 모델·원격 URL·디렉터리 이름만으로 프로젝트 식별자를 만들지 않는다. 공통 디렉터리의 프로젝트 ID를 쓰고 경로 이동은 재연결 검사, 별도 clone은 새 등록으로 처리한다.

## 4. 버전 고정과 실행 계약

1. 플러그인이 제공한 실행기·절차·템플릿을 외부 버전 저장소에 설치한다. 패키지 manifest에 파일별 해시, 패키지 버전, 상태 schema, adapter 계약 버전을 기록한다. 가변 플러그인 cache 경로를 작업의 영구 실행기 경로로 쓰지 않는다.
2. 프로젝트 등록은 기본 프로필과 다음 작업의 기본 런타임을 선택한다. 프로젝트 작업 트리에 파일을 만들지 않는다.
3. 작업 생성 시 실행기·절차·adapter 해시와 유효 설정을 snapshot으로 고정한다. 사용자 비밀 값은 snapshot에 저장하지 않고 필요한 환경변수 이름만 기록한다.
4. 승인 digest에는 기존 스펙·manifest 외에 런타임 식별자와 유효 설정을 포함한다. 모델·운영 규칙 변경도 새 revision과 재승인 대상이다.
5. 작업 명령은 작업 ID의 고정 런타임으로 라우팅한다. 최신 런타임으로 자동 대체하지 않는다. 패키지가 없거나 해시가 다르면 복구 위치를 알리고 중단한다.
6. 업데이트는 다음 작업의 기본값만 바꾼다. 실행 중 작업과 재개 가능한 작업이 참조하는 패키지는 제거하지 않는다. 기본값 롤백도 기존 작업의 계약을 바꾸지 않는다.
7. 상태 schema 변경 시 원본·백업·변환 결과를 분리하며, 구버전 실행기가 새 schema를 쓰지 못하게 검사한다. 백업 없이 제자리 변환하지 않는다.

## 5. 지침·설정 전달

main/pl/work 모두 환경에서 명시적으로 시작하거나 연결하는 진입 경로를 제공한다. 프로젝트를 임의의 에이전트로 열었다고 ohmyPM 역할이 자동 활성화되었다고 간주하지 않는다.

세션별 context에는 역할, 고정 절차 위치·해시, 프로젝트 지침 위치, 스펙·승인 revision, 소유 경로, 실행 명령과 증거 위치를 포함한다. adapter는 이를 시작 입력으로 전달하고 필요한 참조가 읽히는지 준비 검사로 확인한다. 프로젝트 고유 지침은 보존하고 함께 읽는다. 규칙 충돌은 보고하며 환경 지침으로 프로젝트 규칙을 조용히 덮어쓰지 않는다.

설정은 지원되는 세션별 전달 방식과 외부 설정 경로를 우선 사용한다. 특정 CLI 옵션이 있다고 가정하지 않는다. 구현 착수 시 설치된 Orca·모델 CLI에서 기능과 버전을 확인하고 adapter별 지원표를 남긴다.

프로젝트 경로에 설정 파일이 꼭 필요한 도구에만 다음 조건을 적용한다.

- 추적 파일은 수정하지 않는다. 기존 사용자 파일·symlink·junction과 충돌하면 준비를 중단하고 원인을 보고한다.
- 전용 work에 한해 없는 미추적 파일을 생성할 수 있다. 생성 목록·해시·원본 유무·제외 패턴 소유권을 receipt에 기록한다.
- 제외 처리는 로컬 Git metadata에서 하며 .gitignore나 .worktreeinclude를 수정하지 않는다. 기존 exclude 내용과 다른 작업의 사용을 보존한다.
- 회수는 생성 당시 해시와 같은 파일에만 적용한다. 사용자 수정 파일은 남기고 미회수 이유를 기록한다.
- 준비/실행/제출 단계에서 전달물의 강제 stage를 검사한다. ignore가 보안 경계이거나 커밋 방지 장치라고 간주하지 않는다.

자동 전달이 불가능한 adapter는 미지원으로 표시하고 launch하지 않는다. AGENTS.md 수정으로 몰래 우회하지 않는다. 세션 재개도 같은 runtime/context 계약으로 처리한다.

### 요청 분류와 구현 전 경로 검문 (v2 추가)

derived_from: 사용자 제공 odin-3.0 사례와 “위 내용 추가해야해”. 사용자 사례의 요구는 “계좌 화면 만들자 / 사이드바로 내 계좌 / 보고서 화면 만들어서 들어갈 수 있게 해둬”다. 인용된 다른 에이전트의 설치 정상·원인 확정 주장은 이 설계에서 검증한 사실이 아니다. 파일 열람 로그만으로 구현 착수 또는 지침 미전달을 입증할 수 없다.

main은 모든 새 구현 요청에 대해 실제 수정 전에 `처리 경로: 직접 또는 pl 설계 / 근거 / 요청 범위`를 사용자에게 한 줄로 알리고 로컬 접수 기록에 남긴다. 분류에 필요한 파일·설계 열람은 허용한다. 분류에 앞선 코드 수정·설정 변경·구현 work 시작은 허용하지 않는다.

- 새 화면, 새 사용자 기능·흐름, 데이터 계약·권한·외부 연동 변경, 되돌리기 어려운 변경은 pl 설계로 연결한다. 새 화면과 사이드바의 내 계좌/보고서 진입점 요청은 pl 경로다.
- 직접 처리는 범위·완료 기준이 요청에서 명확하고 작고 가역적인 수정에 한한다. 예: 기존 라벨의 지정된 오탈자 수정. 파일 개수나 예상 시간만으로 경로를 정하지 않는다.
- 정보가 부족하면 읽기 조사 후 판단하며, 제품 동작에 관한 선택이 남으면 pl로 연결한다. 단순 경로로 시작했어도 범위가 커지면 수정 전에 재분류한다.
- pl 경로의 work 준비·실행은 해당 설계 revision의 사용자 구현 요청을 확인한다. main이 스스로 설계 승인이나 pl 판정을 대체하지 않는다.
- 라우팅 기록은 요청 원문 식별자, 선택 경로, 근거, 적용 규칙 버전과 설계/승인 참조를 보존한다. ohmyPM 관리 진입점은 기록 누락 시 구현 작업 시작을 거부한다. 자연어 분류의 정확성 자체를 프로그램이 보장한다고 주장하지 않는다.
- main 세션 context와 공통 절차는 같은 버전의 분류 규칙을 참조한다. 프로젝트 AGENTS.md/CLAUDE.md에 블록을 재배포하는 1.0.1 방식은 채택하지 않는다.
- 이미 열린 세션은 새 규칙을 읽었다고 간주하지 않는다. 활성 작업은 기존 계약을 보존하며, 새 요청은 갱신된 context를 확인한 세션으로 연결한다. 설치/doctor 성공과 실제 지침 전달·분류 성공을 별도 검사한다.

검증 시 실제 main 세션에 계좌/보고서 사례, 단순 오탈자, 조사 중 새 사용자 흐름이 드러나는 요청을 입력한다. 각각 pl/직접/재분류가 표시되고, 승인 전 구현 변경이 없으며, 새 세션과 기존 세션 재연결의 규칙 버전이 증거에 남아야 한다. 단순 문자열 포함 테스트로 행동 검증을 대체하지 않는다.

### pl 세션 종료와 재연결 (v3 추가)

derived_from: 사용자 “pl 에이전트가 세션 종료되어 있는 상황도 가정해”. 역할의 지속성은 특정 터미널·모델 대화의 생존에 의존하지 않는다. pl이 없는 상태에서도 main은 접수·읽기 조사·질문 보존을 수행할 수 있으나, pl이 필요한 설계·판정 게이트는 통과시키지 않는다.

- pl 연결 정보는 터미널 핸들 하나가 아니라 프로젝트/역할 식별자, 세션 generation, 연결 receipt와 마지막 확인 상태로 관리한다. 등록된 pl이 없는 경우도 정상 초기 상태로 처리한다.
- pl 상태를 `live / exited / unverifiable`로 구분한다. 터미널 존재와 에이전트 생존을 구별하며 응답 지연·메일 무응답·통신 실패만으로 exited를 선언하지 않는다.
- 최초 미등록 또는 종료가 확인된 경우 main이 합의된 pl 모델로 세션을 준비한다. 프로젝트 지침·고정 runtime·설계 revision·승인·질문·작업 상태·검증 증거를 외부 기록에서 읽도록 연결한다. 대화 이력 복원 기능이 없어도 이 자료로 재구성할 수 있어야 한다.
- 살아 있는 기존 pl이 있으면 그 세션으로 연결한다. 불명확하면 상태 확인과 자료 보존을 계속하며 새 pl을 중복 실행하지 않는다. 사용자가 기존 세션 대체를 명시한 경우에도 이전 소유권을 정산하고 generation을 갱신한 뒤 진행한다.
- 세션 준비는 역할별 lock과 idempotency key/receipt를 사용한다. 중복 요청이나 main 재시작으로 pl이 두 개 생기지 않게 한다. 생성 응답이 끊기면 실제 생성 자원을 대조하고 확인 전 재생성하지 않는다.
- 질문·답변·판정 요청은 터미널이 닫혀도 남는 프로젝트 로컬 outbox에 먼저 보존한다. 새 pl이 요청 ID와 revision을 확인하고 수락한 뒤 처리 완료를 표시한다. 전송 성공과 pl 수락을 구분한다.
- 이전 세션에서 늦게 도착한 답변은 보존하되, generation과 revision이 현재 요청과 맞지 않으면 자동 적용하지 않는다. 새 pl이 기존 설계와 증거를 읽고 수락한 후에만 대기 중 질문·판정을 이어간다.
- 사용자에게 새 pl의 대화 위치와 복구된 작업·revision을 안내한다. 이미 승인된 설계를 세션 종료만으로 다시 승인받지 않는다. 설계 내용이 달라질 때만 재합의한다.
- 기존 통과 판정은 세션 종료만으로 무효화하지 않는다. 원래 commit/base/revision/digest 검증을 만족하면 유지한다. 중간 검토·미완성 답변은 판정으로 승격하지 않고 새 pl이 검토를 이어간다.
- 구현 중 pl이 종료되어도 승인된 범위의 work를 무단 종료하지 않는다. 구현과 증거 보존은 계속 가능하나 필요한 새 판정 전에는 머지하지 않는다. main은 pl의 의미 판단을 대신하지 않는다.

검증 시 pl 미등록, 정상 생존, 종료 확인, 터미널만 생존, 통신 불명, 준비 중 응답 유실, 중복 복구 요청, 이전 generation의 지연 답변을 각각 재현한다. 실제 세션 종료 후 새 pl이 보존된 질문·spec·증거를 읽고 같은 revision의 검토를 이어가는 연동 증거를 남긴다. 이 테스트는 사용자 pl 세션을 종료시키지 않고 전용 테스트 세션으로 수행한다.

## 6. 훅·검증과 제거

신규 설치는 `.githooks/`와 `core.hooksPath`를 만들거나 바꾸지 않는다. 기존 프로젝트 훅은 그대로 동작한다. 역할·변경 범위 검사는 ohmyPM의 prepare/submit/verdict/merge 단계에서 수행한다. 이는 관리 경로의 통합 검사이며, 사용자가 별도로 실행하는 모든 Git 명령을 통제한다고 주장하지 않는다.

해제는 새 작업 시작을 중지하고 환경 연결과 소유 전달물을 회수한다. 활성 작업이 있으면 해당 자원을 제거하지 않는다. 상태·승인·증거는 기본 보존하며 별도 내보내기/백업 경로를 제공한다. 로컬 상태는 clone만으로 복구되지 않는다는 점을 운영 문서에 명시한다. 범용 Git·Orca 환경이나 사용자 설치 도구를 삭제하지 않는다.

## 7. 기존 1.0 설치 전환

전환은 inventory → 검토 가능한 plan → 적용 → 검증 순서다. 일반 등록·업데이트 명령에 전환 삭제를 섞지 않는다.

1. 추적 여부, 현재 내용, 알려진 설치본과의 해시, managed block, 사용자 수정, 기존 훅 설정, 활성 작업을 조사한다. 프로젝트마다 파일별 `유지/이관/삭제 후보/충돌`과 근거를 출력한다. 이름만으로 소유권을 판정하지 않는다.
2. 역할·모델 설정은 외부 프로필로 복사하고 유효 값의 동등성을 확인한다. 제품 설계 문서와 사용자 지침은 유지한다. AGENTS.md/CLAUDE.md는 확인된 managed block만 제거 후보로 삼는다.
3. 실행기·공통 문서·템플릿은 확인된 원본과 동일한 설치본만 자동 제거 후보로 삼는다. 혼합·변경 파일은 보존하고 개별 결정을 요구한다. .gitignore의 일반 Python 패턴처럼 다른 용도로 쓰일 수 있는 항목은 제거하지 않는다.
4. 훅은 파일뿐 아니라 실제 core.hooksPath와 출처를 조사한다. 이전 값을 확인할 증거가 없으면 자동 복원하지 않는다. 사용자 훅으로 바뀌었으면 유지한다.
5. plan에는 적용 전 파일 해시·index·HEAD·설정의 기대값을 담는다. 달라졌으면 재계획한다. 적용 전 원본 바이트·설정·소유권 정보를 백업하고 단계별 receipt를 남긴다. 재실행은 이미 완료된 단계를 대조한다.
6. 기존 활성 작업은 구버전 실행기·상태·설치본을 유지한 채 완료한다. 해당 자원에 대한 제거는 보류한다. 작업을 강제 종료하거나 새 schema로 변환하지 않는다.
7. 먼저 임시 fixture에서 신규 구조와 전환을 검증한다. 이후 ohmyPM 자체 적용 결과를 검토한다. odin-3.0/log_moniteoling 등 실제 타 프로젝트 적용은 각 inventory와 plan을 제시한 후 결정한다.
8. 추적 파일 제거는 한 번의 명시적 프로젝트 정리 변경으로 남길 수 있다. 일반 업데이트에는 정리 커밋이 재발하지 않아야 한다. 푸시·히스토리 재작성은 범위 밖이다.

rollback은 백업 이후 추가 변경을 덮어쓰지 않고 현재 해시를 대조해 복구한다. 복구가 충돌하면 원본과 현재 내용을 모두 보존한다. 새로운 작업이 사용 중인 상태나 패키지를 구버전으로 강제 교체하지 않는다.

## 9. 작업 분해·실행 하네스

공통 실행기와 상태 계약을 함께 바꾸므로 초기 구현은 하나의 work에서 순차 진행한다. 독립성이 확인되지 않은 병렬 work를 열지 않는다.

1. 외부 패키지/프로필/상태 탐색, runtime pin과 승인 digest, schema 호환 구현 — C1/C3/C6.
2. 역할별 adapter/context, 요청 분류·경로 기록·시작 검문, pl 탐색·복구·영속 outbox·generation, 설정 전달·회수, 기존 실행·검증 경로 통합 — C2/C4/C6/C7.
3. inventory/plan/apply/rollback, 기존 installer·rollout 교체, 운영 문서 및 전체 검증 — C5/C6/C8.

work 소유 경로: `plugin/skills/dispatch/`, `plugin/skills/kickoff-workspaces/`, `tests/`, 이 구조를 참조하는 플러그인 문서·manifest(실제 경로를 실행 manifest에서 열거). 제품 PM 점검·보고 기능과 실제 타 프로젝트는 제외한다. pl이 소유하는 이 설계와 판정 문서는 work가 승인 없이 바꾸지 않는다.

하네스: 기존 Python 3.11+ 표준 라이브러리와 Git, 설치된 Orca, 합의된 모델 CLI. 실제 연동 검증 전에 해당 CLI·세션 전달 기능을 확인한다. 임시 저장소·개별 상태 루트·개별 패키지 루트를 사용하며 사용자 전역 설정을 바꾸지 않는다. 추가 의존성·새 서비스는 계획하지 않는다.

main은 사용자 v1 구현 요청과 v2·v3 추가 요청을 함께 기록하고 이 설계의 기준·경로·자원·검증 명령을 execution manifest로 고정한다. 이미 시작한 work가 있으면 기존 변경과 실행 상태를 먼저 정산·보존하고 새 revision을 적용한다. 이전 승인 digest를 새 revision에 재사용하지 않는다. pl은 결과 commit/base/revision/digest와 C1~C8의 실제 증거를 연결해 판정한다. 이후 main이 검증된 결과만 로컬 머지한다.
