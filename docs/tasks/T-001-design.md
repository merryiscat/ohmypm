# T-001 스택 확정과 구성 한 장

- 상태: 검토 반영 v2
- 등급: M — 핵심 케이스의 기술 의존성과 권한 경계 설계(등급 기준: [roles.md](../roles.md)).
- 작성: pl, 2026-09-17

## 목표
기존 스택 결정을 유즈케이스 근거와 연결하고 미결 사항을 분리한다. 후속 스펙이 참조할 `docs/design.md` 구성 한 장을 만든다.

## 범위
- 안: [plan.md](../plan.md)·[usecases.md](../usecases.md)·[setup.md](../setup.md)를 근거로 스택표·주 흐름도·경계·보류를 요약하고 색인에 등재한다.
- 밖: 기존 결정 변경, 미결 사항 확정, 특정 PC의 현재 운영 상태 기록, 상세 API·DB·화면 설계. 코드 읽기·실행·테스트·설치·운영 변경은 하지 않는다.

## 완료 기준 (기준 하나에 확인 방법 하나)
1. [ ] 설계가 한 장 요약이며 기준일과 출처가 있다. 기록된 사실은 `asserted`+출처, 설계 추론은 `inferred`+근거로 표시한다. — 확인: 각 표시와 연결 근거를 문서 대조한다.
2. [ ] 기존 스택 전 항목에 역할·케이스 번호·핵심 수·가중합·채택/보류 상태가 있다. 가중치 3/2/1/1, 같은 케이스 중복 제외, 토대 기준 핵심 ≥2 또는 합 ≥6을 적용하며 예외는 근거를 적는다. — 확인: usecases 합산 규칙 1~3으로 수동 재계산·역추적한다.
3. [ ] 구성도 하나는 로컬 프로젝트→수집→저장·분석→대시보드/알림의 주 흐름만 보여준다. 권한·보류 설명은 그림 밖에 둔다. — 확인: 도식의 입력부터 출력까지 한 경로를 따라 읽는다.
4. [ ] 수집·파싱·화이트리스트 확인과 LLM 소견·반복 원인 분석의 역할을 구분한다. doc-drift의 구현 방식은 미정으로 남긴다. — 확인: usecases의 필요 기술과 역할 설명을 대조한다.
5. [ ] 로컬 실행·PC별 독립 인스턴스와 정시/수동 실행 선택을 설명하며, 특정 PC의 설정값·보류 현황은 넣지 않는다. — 확인: setup의 전제·수동 실행 설명과 대조한다.
6. [ ] 경계 설명에 사용자 등록 화이트리스트, 미등록 행동의 사용자 판단, 삭제·외부 발신·DB 마이그레이션·force push의 자율 허용 제외, 행동별 git 커밋·사유·내역·되돌리기가 있다. — 확인: plan 자율 경계 및 케이스 15와 대조한다.
7. [ ] 케이스 1의 외부 과제셋 의존(다른 케이스는 진행), 4의 heartbeat 재부착, 9의 lychee 범위 결정과 각 재개 조건을 보류 목록에 적는다. git 없는 대상의 제외/init/알림 중 처리는 사용자 결정 질문으로 남긴다. — 확인: 보류 목록을 plan·usecases 및 이 기준과 대조한다.
8. [ ] `docs/index.md`에 design 링크 한 줄이 추가되고, 산출물 변경은 아래 두 파일뿐이다. — 확인: 문서 변경 내역을 읽어 링크와 변경 범위를 확인한다.

## 손대는 파일
- `docs/design.md` — 구성 한 장 신규 작성.
- `docs/index.md` — 새 설계 페이지 링크 한 줄 추가만 허용.
