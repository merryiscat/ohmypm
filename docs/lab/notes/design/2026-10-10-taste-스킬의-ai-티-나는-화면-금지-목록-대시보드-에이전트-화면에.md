# Taste 스킬 'AI 티' 금지 목록 나눠 보기

기준일 2026-10-10 · 핵심 근거: [taste-skill/SKILL.md](https://github.com/Leonxlnx/taste-skill/blob/main/skills/taste-skill/SKILL.md)

## 핵심 요약

**Taste 금지 목록의 절반 이상은 랜딩 페이지용 취향 규칙입니다. 내부 도구 화면에 그대로 옮길 만한 것은 "상태 표시·문구·숫자·접근성" 묶음 정도입니다.**

- Taste 본체가 스스로 대시보드를 대상에서 뺍니다. 첫머리에 "랜딩 페이지, 포트폴리오, 리디자인용이며 대시보드·데이터 표·여러 단계짜리 제품 화면용이 아니다"라고 적혀 있습니다. [출처](https://github.com/Leonxlnx/taste-skill/blob/main/skills/taste-skill/SKILL.md)
- 내부 도구에도 통하고 근거도 있는 규칙: 키보드 포커스 표시, 색만으로 상태를 나타내지 않기, 로딩·빈 화면·오류 상태 만들기, "Oops!" 같은 가벼운 오류 문구 피하기, 숫자 자릿수 맞추기, 상투적인 홍보 문구 피하기.
- 근거 없이 취향뿐인 규칙: Inter 글꼴 금지, 엠대시(—) 금지, 가운뎃점 제한, 순수 검정 금지, 질감·그레인 넣기, "대시보드에 왼쪽 사이드바는 뻔하다".
- 우리 방식과 정면으로 부딪히는 규칙은 "아이콘 SVG를 직접 그리지 마라"입니다. 이 규칙에는 이유가 적혀 있지 않습니다. 이모지 금지는 우리 원칙과 같습니다.

## 스킬 개요

- 저장소 이름은 Taste Skill입니다. AI 코딩 도구가 만드는 "뻔한 화면"을 줄이려는 지침 묶음이고, MIT 사용권으로 공개돼 있습니다. 조사 시점 페이지에 별 94.2k개가 표시됐습니다. [출처](https://github.com/Leonxlnx/taste-skill)
- 이번에 본 스킬은 셋입니다.
  - **taste-skill**: 기본형입니다. 변화 폭·움직임·밀도라는 세 가지 조절값(DESIGN_VARIANCE, MOTION_INTENSITY, VISUAL_DENSITY)을 씁니다.
  - **redesign-skill**: 이미 있는 화면을 점검하는 목록형입니다.
  - **minimalist-skill**: 차분한 편집물 느낌을 내는 스타일 지침입니다.
- 깔고 들어가는 기술 묶음은 다음과 같습니다. React/Next.js, Tailwind v4(미리 만든 CSS 클래스 묶음), Motion(애니메이션 라이브러리), 아이콘 라이브러리(Phosphor → HugeIcons → Radix → Tabler 순서). 글꼴은 next/font 또는 직접 올린 파일을 씁니다. [출처](https://github.com/Leonxlnx/taste-skill/blob/main/skills/taste-skill/SKILL.md)

## 티 나는 패턴

세 문서에 흩어진 금지 항목을 묶으면 아래와 같습니다.

### 겉모습

- 네온·바깥쪽 빛 번짐, 큰 제목에 그라데이션 글자, 보라·파랑 계열 "AI 그라데이션"
- 순수 검정(#000000), 채도 높은 강조색, 강조색 두 개 이상, 따뜻한 회색과 차가운 회색 섞기
- 기본 그림자(테두리+그림자+흰 배경 카드), 모든 요소에 같은 모서리 둥글기
- 사용자 지정 마우스 커서
- (minimalist) 그라데이션 전면 금지. 그림자는 투명도 0.05 미만. 큰 컨테이너는 알약 모양 금지 [출처](https://github.com/Leonxlnx/taste-skill/blob/main/skills/minimalist-skill/SKILL.md)

### 글자

- Inter를 기본 글꼴로 쓰기. minimalist는 Roboto, Open Sans도 금지합니다.
- 지나치게 큰 H1, 굵기를 400·700 두 가지만 쓰기, 숫자를 가변폭으로 두기
- 모든 소제목을 대문자로 쓰기, 모든 제목을 단어마다 대문자로 시작하기(Title Case), 마지막 줄에 단어 하나만 남기기 [출처](https://github.com/Leonxlnx/taste-skill/blob/main/skills/redesign-skill/SKILL.md)

### 배치

- 같은 크기 카드 세 개를 가로로 늘어놓기, 전부 가운데 정렬·좌우 대칭
- 카드 높이를 억지로 맞추기, 겹침이나 깊이감이 없음
- "대시보드는 늘 왼쪽 사이드바" [출처](https://github.com/Leonxlnx/taste-skill/blob/main/skills/redesign-skill/SKILL.md)

### 내용과 문구

- John Doe 같은 가짜 이름, 99.99%·50% 같은 딱 떨어지는 가짜 숫자, Acme·Nexus 같은 가짜 회사명, Lorem Ipsum(뜻 없는 채움 글)
- "Elevate·Seamless·Unleash·Next-Gen" 같은 상투어
- 성공 메시지에 느낌표, "Oops!" 오류 문구, 수동태
- 엠대시(—) 전면 금지. 범위 표시에 엔대시(–)도 금지 [출처](https://github.com/Leonxlnx/taste-skill/blob/main/skills/taste-skill/SKILL.md)

### 실제 출시물에서 보이는 흔적 (9.F)

- 첫 화면의 버전 표시(BETA, v0.6), "001 · Capabilities" 같은 번호 붙은 소제목, "Step 1" 같은 단계 라벨
- 장식용 색 점(메뉴·목록·배지 위), 가운뎃점(·) 남용(한 줄에 하나까지)
- 사진 출처 캡션, "스크롤하세요" 안내, 날씨·지역 띠, 세로 회전 글자
- 긴 목록의 모든 행에 가는 구분선, 비교 막대의 배경 트랙 [출처](https://github.com/Leonxlnx/taste-skill/blob/main/skills/taste-skill/SKILL.md)

### 부품과 아이콘

- 아이콘 SVG를 직접 그리기, 장식 SVG를 직접 그리기, div로 흉내 낸 제품 스크린샷
- Lucide·Feather만 쓰기, "출시 = 로켓·보안 = 방패" 같은 뻔한 비유, 아이콘 선 굵기가 제각각
- shadcn/ui(React 부품 모음) 기본 모양 그대로 쓰기
- 버튼은 늘 "채운 버튼 하나 + 테두리 버튼 하나", 'New'·'Beta' 알약 배지, 무엇이든 모달로 띄우기
- 자주 묻는 질문 아코디언, 점 달린 후기 슬라이드, 세 칸 가격표, 링크로 가득한 4단 하단 [출처](https://github.com/Leonxlnx/taste-skill/blob/main/skills/redesign-skill/SKILL.md)

### 상태와 동작 (redesign)

- 마우스 올림·누름 반응이 없음, 전환 시간이 0초
- 포커스 링 없음, 로딩·빈 화면·오류 상태 없음
- 현재 페이지 표시 없음
- top·left·width·height 값을 바꾸는 애니메이션 [출처](https://github.com/Leonxlnx/taste-skill/blob/main/skills/redesign-skill/SKILL.md)

## 내부 도구에 통함

대시보드·칸반·채팅·문서 화면에도 맞는 규칙입니다. 근거 강도는 "기준 있음 / 가이드 있음 / 취향"으로 표시했습니다.

| 규칙 | 근거 강도 | 근거 |
|---|---|---|
| 키보드 포커스가 눈에 보여야 함 | 기준 있음 | WCAG(국제 웹 접근성 기준) 2.4.7 "포커스 보임" [출처](https://www.w3.org/WAI/WCAG22/Understanding/focus-visible.html) |
| 상태를 색 점 하나로만 보여주지 않기 | 기준 있음 | WCAG 1.4.1 "색만으로 정보 전달 금지" [출처](https://www.w3.org/WAI/WCAG22/Understanding/use-of-color.html). IBM Carbon은 토글 상태를 색과 글자로 함께 보여줍니다 [출처](https://www.carbondesignsystem.com/components/toggle/accessibility/) |
| 글자 대비 4.5:1 이상 | 기준 있음 | WCAG 1.4.3. Taste도 4.5.절에서 같은 값을 요구합니다 [출처](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html) |
| 움직임 줄이기 설정 존중 | 기준 있음(AAA 등급) | WCAG 2.3.3 [출처](https://www.w3.org/WAI/WCAG22/Understanding/animation-from-interactions.html) |
| 빈 화면을 비워두지 말고 이유와 다음 행동을 보여주기 | 가이드 있음 | NN/g(사용성 연구 회사)는 빈 화면이 상태 전달·기능 안내·바로가기 역할을 한다고 봅니다 [출처](https://www.nngroup.com/articles/empty-state-interface-design/). SAP Fiori도 같은 구조를 권합니다 [출처](https://www.sap.com/design-system/fiori-design-web/v1-96/foundations/best-practices/global-patterns/designing-for-empty-states) |
| 화면 전체를 불러올 때는 스켈레톤(뼈대 미리보기), 짧은 동작에는 스피너 | 가이드 있음 | NN/g 비교 영상 [출처](https://www.nngroup.com/videos/skeleton-screens-vs-progress-bars-vs-spinners/) |
| 오류 문구에 농담·"Oops" 쓰지 않기 | 가이드 있음 | Google 기술 문서 작성 가이드: 오류는 사용자를 짜증 나게 하므로 유머를 피하라 [출처](https://developers.google.com/tech-writing/error-messages/set-tone) |
| 숫자는 고정폭(tabular)으로 맞추기 | 가이드 있음 | CSS `font-variant-numeric: tabular-nums`. 표 정렬과 바뀌는 숫자의 흔들림 방지에 씁니다 [출처](https://dialtone.dialpad.com/utilities/typography/font-variant-numeric.html) |
| 현재 위치 표시, 누름·마우스 올림 반응 | 일반 관행 | 이번 조사에서 1차 출처는 따로 확인하지 못했습니다 |
| 애니메이션은 transform·opacity로 | 일반 관행 | 성능 관련 관행입니다. 이번에 1차 출처는 따로 확인하지 못했습니다 |
| 의미 있는 HTML 태그, 이미지 대체 글, z-index 순서 정하기 | 대체 글은 기준 있음(WCAG 1.1.1), 나머지는 관행 | — |
| 상투적 홍보 문구, 가짜 이름·숫자 쓰지 않기 | 취향에 가까운 관행 | 내부 도구에서는 예시 데이터나 시연 화면에만 해당합니다 |
| 이모지 금지 | 취향(우리 원칙과 같음) | Taste 3.D도 기본값은 쓰지 말라는 쪽입니다 |
| 강조색 하나, 회색 계열 하나 | 취향 | 일관성 면에서는 합리적이지만 기준 문서는 없습니다 |

AI 제품 쪽 한 가지를 덧붙입니다. "보라·파랑 그라데이션이 AI 티"라는 지적은 랜딩 페이지 얘기로 나왔습니다. 그래도 에이전트 화면에서 AI 기능을 표시할 때도 같은 인상을 줄 수 있습니다. 다만 이것도 취향입니다.

## 랜딩 전용

내부 도구에는 해당이 없거나 오히려 맞지 않는 규칙입니다.

- **첫 화면·마케팅 요소**: 버전 표시, 스크롤 안내, 사진 출처, 날씨 띠, 세 칸 가격표, 후기 슬라이드, 자주 묻는 질문 아코디언, 4단 하단, 쿠키 동의, 맞춤 404 페이지, 공유용 메타 태그.
- **같은 카드 세 개 금지, 대칭 금지, 겹침·깊이감, 그레인·질감, 큰 여백(py-24~32)**: 정보 밀도가 중요한 화면에서는 오히려 방해가 됩니다.
- **긴 목록의 행마다 구분선 금지**: Taste도 데이터 밀도가 높은 단계(7절 "Cockpit")에서는 "카드 없이 1px 선으로 데이터를 나눈다"고 적어 서로 엇갈립니다. 표·칸반 목록에서는 행 구분선이 정상입니다. [출처](https://github.com/Leonxlnx/taste-skill/blob/main/skills/taste-skill/SKILL.md)
- **"대시보드는 늘 왼쪽 사이드바"를 피하라**: 취향입니다. 내부 도구에서는 사이드바가 익숙한 구조여서 바꿀 이유가 약합니다.
- **"Step 1" 단계 라벨 금지**: 마법사 화면이나 진행 표시에서는 단계 번호가 필요한 정보입니다.
- **Title Case 금지, 소제목 대문자 금지**: 영어 문제라서 한국어 화면과는 관계가 거의 없습니다. Atlassian도 영어 화면에 문장형 대소문자를 씁니다. [출처](https://atlassian.design/foundations/content/language-and-grammar)

### 근거 없는 취향 규칙

- **Inter 금지**: Inter는 원래 화면 UI용으로 만든 글꼴입니다. 작은 크기 가독성, 고정폭 숫자, 0과 o 구분 기능이 있고 Figma UI에도 쓰입니다. 내부 도구라면 금지할 이유가 약합니다. [출처](https://rsms.me/work/inter/)
- **엠대시(—)·가운뎃점 제한**: "AI가 쓴 글 같다"는 인상론입니다. 기준 문서는 없습니다.
- **순수 검정 금지, 기본 그림자 금지, 모서리 둥글기 다양화**: 미감의 문제입니다.

## 우리와 충돌

ohmyPM 기준으로 보면, 화면은 외부 라이브러리 없는 순수 HTML이고 아이콘은 인라인 SVG이며 이모지는 쓰지 않습니다.

| Taste 규칙 | 충돌 정도 | 메모 |
|---|---|---|
| "아이콘 SVG를 절대 직접 그리지 마라"(3.C, 9.E) | 정면 충돌 | 이유가 적혀 있지 않습니다. 대안도 "라이브러리를 하나 더 깔아라"뿐입니다. 숨은 목적은 선 굵기 통일과 한 계열 유지로 보이니, 그 목적만 가져오면 됩니다 |
| React·Tailwind·Motion·next/font 전제 | 충돌 | 클래스 이름(py-24, max-w-5xl 등)과 예시 코드는 그대로 못 씁니다. 수치(간격·전환 시간)만 옮길 수 있습니다 |
| shadcn/ui 기본 모양 금지 | 해당 없음 | 쓰지 않습니다 |
| Picsum 사진 자리표시, 외부 글꼴(Geist 등) | 충돌 | 외부 요청이 생깁니다. 내부 도구에는 필요가 없습니다 |
| 이모지 금지 | 일치 | — |
| minimalist의 "Lucide·Feather 같은 얇은 선 아이콘 금지" | 취향 | 직접 그리는 아이콘의 선 굵기를 정할 때 참고만 하면 됩니다 |

minimalist 스킬은 문서 안에서도 엇갈립니다. 2절에서 그라데이션을 금지해 놓고, 6~7절에서는 은은한 원형 그라데이션을 허용합니다. [출처](https://github.com/Leonxlnx/taste-skill/blob/main/skills/minimalist-skill/SKILL.md)

## 우리 쪽 적용

**제안일 뿐 결정이 아닙니다.** ohmyPM 코드는 이번에 열어 보지 않았습니다. 아래는 지금 화면이 이미 지키는지 확인해 볼 후보입니다.

### 화면 다듬기 점검표 후보 (10개)

1. 키보드 Tab으로 이동할 때 모든 버튼·링크·카드에 포커스 테두리가 보이는가 (WCAG 2.4.7)
2. 상태(진행 중·완료·막힘)를 색 점 하나로만 보여주지 않고 글자나 모양을 함께 쓰는가 (WCAG 1.4.1)
3. 장식용 색 점을 없앴는가. 점은 실제 상태를 뜻할 때만 쓰는가
4. 칸반 열·채팅·문서 목록이 비었을 때 "왜 비었는지 + 다음에 할 일" 한 줄과 버튼이 있는가
5. 목록·보드를 불러오는 동안 뼈대 미리보기, 저장처럼 짧은 동작에는 작은 스피너로 구분했는가
6. 오류 문구가 무엇이 잘못됐고 어떻게 고치는지 말하는가. 느낌표·"앗!"·농담이 없는가
7. 숫자 열(개수·날짜·비용)에 `font-variant-numeric: tabular-nums`를 켰는가
8. 인라인 SVG 아이콘의 선 굵기와 크기가 한 가지로 통일돼 있는가 (Taste 규칙 중 목적만 가져온 것)
9. 버튼에 마우스 올림·누름 반응이 있는가. 사이드바·탭에 현재 위치가 표시되는가
10. 애니메이션이 있다면 `prefers-reduced-motion`(움직임 줄이기 설정)을 존중하는가. 글자 대비는 4.5:1 이상인가

점검표에 넣지 않은 것은 Inter 금지, 엠대시 금지, 행 구분선 금지, 사이드바 회피입니다. 이유는 근거가 없거나 내부 도구와 맞지 않아서입니다.

## 확인 못 한 것

- **Taste 본체의 적용 범위가 안에서 엇갈립니다.** 첫머리와 13절은 대시보드를 제외합니다. 그런데 0절은 "모든 규칙은 맥락에 따른다", 14절은 "점검표는 선택이 아니다"라고 해서 어느 쪽이 우선인지 정리돼 있지 않습니다.
- **대비 목표도 엇갈립니다.** 4.5절은 WCAG AA, 6.C절은 "본문은 AAA", 8.B절은 첫 화면 문구에 AAA를 목표로 둡니다.
- **문서를 원문 그대로 다 읽지 못했습니다.** 세 SKILL.md는 가져오기 도구가 요약해 준 내용과 짧은 인용으로 봤습니다. 절 번호와 문구에 작은 차이가 있을 수 있습니다. 저장소의 마지막 수정 날짜도 확인하지 못했습니다.
- **NN/g 원문은 요약만 확인했습니다.** 빈 화면과 스켈레톤 관련 글의 전문은 못 읽었습니다. "Oops" 오류 문구에 대한 NN/g의 입장도 찾지 못해 Google 가이드로 대신했습니다.
- **Atlassian의 느낌표 규칙**("한 페이지에 하나까지")은 공식 사이트가 아닌 복제본에서만 봤습니다.
- **Carbon의 상태 표시 전용 페이지**(색·모양·글자 조합 규칙)는 찾지 못했습니다. 토글·진행 막대 페이지로 대신했습니다.
- **ohmyPM 화면이 위 점검표를 지금 얼마나 지키는지**는 코드를 보지 않아 모릅니다.
