# Web Design Guidelines 스킬 평가

기준 날짜: 2026-10-10 · 핵심 근거: [규칙 원문 command.md](https://raw.githubusercontent.com/vercel-labs/web-interface-guidelines/main/command.md), [고정 요청 이슈 #316](https://github.com/vercel-labs/agent-skills/issues/316)

## 핵심 요약

**계속 깔아 둘 이유는 약하다. 사용자 범위 설치는 지우고, 쓸 만한 규칙만 ohmyPM 점검표에 옮겨 적는 쪽을 제안한다.**

- 이 PC에 깔린 스킬은 Vercel 원본과 내용이 같다. 그런데 스킬 파일 자체에는 규칙이 없다. 실행할 때마다 GitHub의 `main` 가지에 있는 규칙 파일을 받아 와서 그대로 지시로 따른다. 이 파일은 미리 알리지 않고 바뀔 수 있다.
- 규칙 약 104개 가운데 오늘 ohmyPM에 반영한 항목(포커스 표시, 키보드 조작, 움직임 줄이기, 빈 화면 안내, 숫자 폭 맞춤 등)과 겹치는 것이 많다. 다음 검사에서 새로 잡힐 만한 것은 일부뿐이다.
- 규칙 상당수가 React·Next.js(웹 화면을 짜는 도구)와 영어 화면을 전제로 한다. 단일 HTML·한국어 화면인 ohmyPM에서는 쓸데없는 지적이 섞인다. 출력 형식에 체크 표시(`✓ pass`)가 들어 있어 우리 이모지·장식 기호 금지 규칙과도 부딪친다.
- `파일:줄` 보고는 pages.py에서도 실제 줄을 가리키므로 쓸 수 있다. 다만 파일 하나가 1,276줄이라, 한 번 검사하면 그 파일 전체를 읽는 셈이다.

## 규칙 구성

17개 절, 규칙 약 104개다. 주요 묶음은 접근성(12), 포커스(5), 입력 양식(11), 애니메이션(8), 글자 모양(6), 내용 처리(4), 성능(8), 탐색·상태(4), 터치(7), 다크 모드(3), 언어·지역(4), 하이드레이션(3), 마우스 올림 상태(2), 문구(7), 금지 패턴(14) [출처](https://raw.githubusercontent.com/vercel-labs/web-interface-guidelines/main/command.md).

- **출력 형식**: 파일마다 `## 경로` 제목을 달고 그 아래 `파일:줄 - 문제` 줄을 짧게 쓴다. 문제가 없는 파일에는 `✓ pass`를 적는다.
- **React 전용 규칙**: 하이드레이션(서버가 만든 화면에 브라우저가 기능을 붙이는 과정) 3개, `onChange`·`defaultValue`, 50개가 넘는 목록의 가상화(보이는 부분만 그리기) 등은 React를 쓰지 않는 ohmyPM에는 맞지 않는다.
- **영어 화면 전용 규칙**: 제목과 버튼의 Title Case(단어 첫 글자 대문자), 둥근 따옴표, 앰퍼샌드(&) 사용 등은 한국어 화면에 해당하지 않는다.
- **대비 규칙**: 색 대비를 WCAG(웹 접근성 국제 기준) 수치로 검사하는 규칙은 따로 없다. "마우스 올림·누름·포커스 상태는 평소보다 대비가 커야 한다" 한 줄뿐이다.

### 다음 검사에서 새로 잡힐 만한 것

- 사이드바 메뉴가 `<div onclick>`이다(326~331줄). 우리는 role=button을 붙여 고쳤지만, 스킬 규칙은 "이동에는 링크(`<a>`)를 써라", "div에 클릭 처리 금지"라서 여전히 걸린다. 근본적인 개선 지적이라 의미가 있다.
- `go('#/...')`처럼 코드로 화면을 옮기는 클릭은 Ctrl+클릭으로 새 탭에서 열 수 없다. "링크로 해야 수정키 클릭이 된다" 규칙에 걸린다.
- 그 밖에 확인 대상: 본문 바로가기 링크, 비동기 알림의 aria-live(화면 읽기 프로그램에 바뀐 내용을 알려 주는 속성), 지우는 동작의 확인·되돌리기, 이미지 크기 지정, `transition: all` 사용 여부. 이 중 지우기 확인은 이미 appConfirm으로 하고 있다(1257줄).

## 단일 HTML 구조

- pages.py는 `_HTML = r"""..."""` 한 덩어리가 22~1268줄을 차지한다. 에이전트는 pages.py를 그대로 읽으므로 `pages.py:326` 같은 보고는 실제 줄과 맞는다. 줄 번호를 따로 바꿔 계산할 필요가 없다.
- 화면의 상당 부분이 자바스크립트 문자열(`innerHTML = '...'`)로 만들어진다. 그래서 "몇 번 줄의 어떤 요소" 수준으로는 잘 가리키지만, 실제로 화면에 그려진 결과(색 대비, 겹침, 포커스 순서)는 코드만 읽어서는 확인할 수 없다.
- 1,276줄 파일 하나를 통째로 읽으므로 검사 한 번에 컨텍스트(모델이 한 번에 보는 분량)를 꽤 쓴다. 맥스 요금제 세션 단위로 보면 한 번은 괜찮지만, 매번 돌리기에는 부담이 있다.

- 실제 사용자가 직접 써 본 상세 후기는 찾지 못했다. 검색 결과는 대부분 스킬 목록 사이트의 소개 글로, 사실상 홍보·요약이다 [출처](https://www.mdskills.ai/de/skills/web-design-guidelines) [출처](https://vibeindex.ai/skills/vercel-labs/agent-skills/web-design-guidelines).
- 그나마 독립 측정에 가까운 것은 #300 작성자의 1회 시험이다. 스킬을 켜면 5점 만점에 4점, 끄면 2점이었다. 다만 작성자 스스로 그 차이가 받아 온 규칙 덕분이라기보다 "검사하라는 맥락을 준 효과"로 보인다고 적었다. 시험 1회라 근거로는 약하다 [출처](https://github.com/vercel-labs/agent-skills/issues/300).
- 한 목록 사이트는 skills.sh 보안 점검에서 이 스킬을 "중간 위험"으로 표시했다고 적었다. 판정 근거는 확인하지 못했다 [출처](https://moltchat-agent-commons.onrender.com/wiki/web-design-guidelines_skill_(vercel-labs%2Fagent-skills)).

## 대안 비교

| 방법 | 잘하는 것 | 못하는 것 |
|---|---|---|
| 이 스킬 (코드 읽기) | 코드 습관 문제를 `파일:줄`로 지적. 설치 쉬움 | 실제 대비·렌더링은 못 봄. 매번 외부에서 지시를 받음 |
| axe-core·Lighthouse (실제 화면 검사 도구) | 그려진 화면에서 대비·이름표·제목 계층을 수치로 확인 | 코드 줄까지는 못 짚음. 브라우저 실행 필요 |

| 우리 점검표 (pages.py 주석 + 문서) | 한국어·이모지 금지 등 우리 규칙 반영 | 넓은 범위를 다 덮지는 못함 |

"코드 읽기 검사는 빠른 1차 점검으로 쓰고, 자동 도구와 화면 읽기 프로그램으로 직접 확인하는 것을 함께 하라"는 권고는 목록 사이트들에서도 공통이다 [출처](https://moltchat-agent-commons.onrender.com/wiki/web-design-guidelines_skill_(vercel-labs%2Fagent-skills).md).

## 우리 쪽 적용

이 절은 제안일 뿐 결정이 아니다.

**제안: 사용자 범위 설치(`~/.claude/skills/web-design-guidelines`)는 지우고, 아이디어만 참고한다.**

이유:
- 사용자 범위에 깔린 스킬은 ohmyPM이 헤드리스(화면 없이 자동 실행)로 부르는 약 40개 프로젝트 담당 호출 모두에 함께 실린다. 담당이 "접근성 점검" 같은 말을 하면 스킬이 켜지고, 고정되지 않은 외부 파일을 지시로 받아 따르게 된다. 프로젝트 대부분은 웹 화면이 없어서 얻는 것은 없고 위험만 남는다.
- 오늘 반영한 점검표가 핵심 항목을 이미 덮고 있다. 남는 이득은 "메뉴를 링크로 바꾸기" 정도다.
- 출력의 `✓ pass`, Title Case, 둥근 따옴표 규칙은 우리 화면 규칙과 부딪쳐 매번 걸러 내야 한다.

해 볼 만한 것:
1. command.md에서 우리에게 맞는 20개 안팎(포커스, 키보드, 이름표, 링크·버튼 구분, 빈 상태, 움직임 줄이기, 지우기 확인, aria-live)만 골라 ohmyPM `docs/`의 화면 점검표에 우리말로 옮긴다. 출처 커밋 날짜(2026-10-05)를 함께 적는다.
2. 사이드바 메뉴 `<div onclick>`를 `<a href="#/...">`로 바꾸는 일을 다음 화면 작업 후보에 넣는다.
3. 그래도 이 스킬을 한 번 돌려 보고 싶다면, 규칙 파일을 특정 커밋 주소로 고정한 사본을 ohmyPM 프로젝트 범위(`.claude/skills/`)에만 두고 pages.py 한 파일만 검사한 뒤 지운다.
4. 대비 검사는 이 스킬로 할 수 없다. 필요하면 axe-core 같은 실제 화면 검사를 따로 검토한다.

버려지는 안("사용자 범위에 계속 둔다")의 재검토 조건(사용자와 확정 필요): #316·#317이 받아들여져 원본이 규칙을 특정 판으로 고정하게 되면 다시 본다. 기록처는 ohmyPM `docs/`의 적절한 문서다.
